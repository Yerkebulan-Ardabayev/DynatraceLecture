## 🎓 Часть 1. Что такое Dynatrace Managed и зачем он нужен

### Определение

Dynatrace Managed — это **платформа полного наблюдения за ИТ-системой**, развёрнутая полностью на инфраструктуре клиента. По-английски «полное наблюдение» называется *full-stack observability* — «сквозное наблюдение за всеми уровнями технологического стека».

Слово **observability** (наблюдаемость) — относительно новое в индустрии. Оно отличается от старого **monitoring** (мониторинг). Разница такая:

- **Monitoring** — это «мы заранее знаем, что может сломаться, и для каждого случая написали правило, которое сработает». Классический пример: правило «если CPU больше 80% дольше 5 минут — алерт».
- **Observability** — это «мы собираем максимум сырых данных и при необходимости можем задать любой вопрос, даже тот, который не предсказали». Это требует богатого набора данных: метрики, логи, трейсы — и связи между ними.

Dynatrace относится ко второму классу. Платформа собирает три вида данных:

- **Метрики** (metrics) — числовые показатели во времени. Например, «загрузка процессора 45%» или «время ответа сайта 220 миллисекунд».
- **Логи** (logs) — текстовые записи событий, которые программы пишут в файлы. Например, «20:14:33 пользователь Иванов вошёл в систему».
- **Трейсы** (traces, от англ. *trace* — «след») — маршрут одного конкретного запроса пользователя через все сервисы и базы данных. Видно, на каком шаге сколько времени потрачено.

Часто это называют **«три столпа observability»** (three pillars of observability).

### Почему именно Managed-вариант

Dynatrace Managed — это **on-premise развёртывание**, то есть установка серверной части полностью на инфраструктуре клиента. Это единственный вариант, который подходит:

- **Банкам** — требования финансового регулятора, локализация данных
- **Государственным организациям** — требования законодательства о хранении данных в стране
- **Военным и спецслужбам** — изолированная сеть без выхода в интернет
- **Крупным телекомам и энергетике** — требования по защите критической инфраструктуры

В нашем кейсе клиенты — банки и крупные компании Казахстана с **полностью изолированной (air-gapped) сетью**. «Air-gapped» дословно «через воздушный зазор» — означает, что между корпоративной сетью клиента и интернетом нет физического подключения. Никакие данные мониторинга не должны и не могут уйти за пределы периметра.

Отсюда следует главное архитектурное ограничение. У клиента **нет доступа** к облачным сервисам Dynatrace — Mission Control, customer portal в реальном времени, Hub-marketplace через интернет. Все обновления, расширения, метаданные приходят как файлы, скачанные администратором с другой машины.

### Три технологических принципа Dynatrace

Платформа построена вокруг трёх взаимосвязанных идей, которые пронизывают весь курс и определяют, как выглядит и ведёт себя интерфейс.

**1. Автоматическое обнаружение (auto-discovery).**
После установки OneAgent на хост платформа сама находит процессы, сервисы, контейнеры и связи между ними. В UI отдельно «добавлять сервис» не нужно — через несколько минут в карте инфраструктуры появляется то, что реально запущено. Это объясняет, почему в Dynatrace нет привычного экрана «Добавить объект мониторинга»: список строится из наблюдаемого состояния, а не из настроек.

**2. Davis AI — встроенный анализатор.**
Поверх собранных метрик и трейсов работает движок, который строит базовые линии, корреляции и находит первопричины инцидентов. Из этого принципа вытекает устройство раздела **Problems**: Davis группирует связанные аномалии в один инцидент с деревом причинно-следственных связей, а не показывает отдельный алерт по каждой метрике.

**3. PurePath — сквозной трейсинг каждого запроса.**
Каждому входящему запросу присваивается идентификатор, который сохраняется при переходе между языками и технологиями (Java → .NET → Python → MySQL → Redis). Благодаря этому в интерфейсе работает анализ одного конкретного запроса «от кнопки на фронте до SQL-запроса в базе». PurePath — причина, почему в Dynatrace есть раздел **Distributed traces** и почему карточка сервиса показывает зависимости по реальным вызовам, а не по декларации.

## 🎓 Часть 2. Три уровня архитектуры Dynatrace Managed

Архитектура состоит из трёх уровней. Любая проблема с Dynatrace на проекте в итоге сводится к проблеме на одном из них — полезно держать эту структуру в голове с первого дня.

### Уровень 1 — OneAgent (агент на каждом сервере)

OneAgent — это **программа-сборщик данных**, которая ставится на каждый сервер, который мы хотим мониторить. Слово «agent» переводится как «агент» — программа, которая работает в фоне и что-то делает (в нашем случае — собирает данные).

#### Где OneAgent ставится

- **Bare-metal сервер** (английское выражение, дословно «голое железо»). Это **физический сервер**, на котором операционная система установлена напрямую, без виртуализации. Например, физический Dell PowerEdge в стойке дата-центра.
- **Виртуальная машина (ВМ)**. Программная имитация сервера внутри гипервизора. Гипервизор — это специальная программа, которая позволяет на одном физическом сервере запустить несколько виртуальных серверов, каждый со своей операционной системой. Самые известные гипервизоры в банках: VMware ESXi, Microsoft Hyper-V, KVM, Proxmox. Для OneAgent виртуальная машина выглядит как обычный сервер.
- **Контейнер**. Изолированная среда выполнения программы внутри операционной системы хоста. Самый известный контейнерный движок — Docker. В отличие от виртуальной машины, контейнер не имеет своей операционной системы — он делит её с хостом. Поэтому контейнеры запускаются за секунды, а не за минуты. OneAgent ставится на хост, на котором работают контейнеры, и автоматически их видит.

#### Поддерживаемые операционные системы

- **Linux** — поддерживаются основные enterprise-семейства (RHEL, Rocky, AlmaLinux, Ubuntu LTS, SLES, Debian) на архитектурах x64, ARM64 (AArch64), s390x, PPC64-LE; точный диапазон версий «from / to» меняется от релиза к релизу OneAgent и фиксируется в [OneAgent platform and capability support matrix](https://docs.dynatrace.com/docs/ingest-from/technology-support/oneagent-platform-and-capability-support-matrix). Для банков и госорганизаций с требованиями национального регулятора — сертифицированные Linux-сборки, которые клиент использует в остальной инфраструктуре; совместимость конкретной сборки сверяется в той же матрице.
- **Windows** — Windows Server и клиентские Windows; конкретные версии — в матрице совместимости.
- **AIX**, **Solaris** — поддерживаются для крупных банков с UNIX-семейством на бэкенде; диапазон версий — там же.
- **z/OS** — отдельный продукт OneAgent for z/OS для мейнфреймов IBM, актуально для банков с легаси-ядром. <!-- last-verified: 2026-04-27 source: docs.dynatrace.com/docs/ingest-from/technology-support/oneagent-platform-and-capability-support-matrix -->

#### Потребление ресурсов

OneAgent спроектирован как лёгкий агент и в типовой full-stack-инсталляции потребляет небольшую долю CPU хоста и сотни мегабайт оперативной памяти. Точный overhead зависит от режима мониторинга, количества инструментируемых процессов и активных технологических модулей — поэтому официальные рекомендации всегда даются диапазоном и измеряются на пилоте конкретной инсталляции. Для сравнения: одно тяжёлое приложение Java запросто берёт несколько гигабайт памяти, то есть агент не становится заметной статьёй расходов на фоне прикладной нагрузки.

#### Что собирает OneAgent

| Тип данных | Что именно |
|---|---|
| Метрики операционной системы | Загрузка процессора (по ядрам), использование памяти (RSS, виртуальная), чтение/запись с диска (IOPS, throughput), сетевой трафик, открытые TCP/UDP-соединения, открытые файлы |
| Метрики процессов | Сколько каждый процесс ест процессор и память, сколько потоков создал, сколько памяти выделил под кучу (heap — область памяти, где Java/.NET хранят объекты), сколько garbage collection сделал, сколько файлов открыл |
| Трейсы запросов | Полный путь HTTP-запроса от веб-сервера через приложение до базы данных. Каждый шаг с таймингом в наносекундах. Это PurePath — фирменная технология Dynatrace |
| Логи | Системные логи (`/var/log/syslog` в Linux, Event Log в Windows), логи отдельных приложений (через настройку Log Monitoring), логи контейнеров (stdout/stderr из Docker) |
| Сетевые соединения | Кто с кем связан по сети, время отклика между процессами, retransmissions (повторные передачи TCP — признак проблем сети) |
| RUM (Real User Monitoring) | Если приложение веб — OneAgent внедряет JavaScript-сниппет в HTML-ответы. Этот сниппет на стороне браузера собирает данные о реальных пользователях |

#### Как OneAgent видит код приложения, не меняя сам этот код

OneAgent делает **глубокую инструментацию** — встраивает свои датчики в чужой код, не модифицируя исходные файлы программы. По-английски это называется *deep code-level instrumentation*. Технически работает так:

- Для **Java**. Java-программа выполняется внутри особой среды — JVM (Java Virtual Machine, виртуальная машина Java). При старте JVM OneAgent подгружается через стандартный встроенный механизм — флаг `-javaagent`. После этого OneAgent перехватывает байткод программы. Байткод (bytecode) — это промежуточный машинный код, в который компилятор Java переводит исходный код перед запуском. OneAgent добавляет в нужные места байткода вызовы своих сборщиков данных. Программе кажется, что её код не изменился, но при этом каждый вызов метода теперь измеряется.
- Для **.NET** (платформа Microsoft, аналог Java). Используется тот же подход через стандартный API под названием CLR Profiling API. CLR — Common Language Runtime, среда выполнения .NET-кода.
- Для **Node.js** (платформа для JavaScript на сервере). Через подмену стандартных модулей в момент `require`.
- Для **Python**. Через установку тонкого нативного модуля и хуки в импортах.
- Для **Go**. Это сложный случай — Go компилируется в нативный бинарь без runtime. OneAgent поддерживает автоматическую инструментацию 64-битных Go-исполняемых файлов на x86 и ARM64 (детали в [Supported Go versions](https://docs.dynatrace.com/docs/ingest-from/technology-support/application-software/go)); конкретный механизм встраивания — внутреннее устройство OneAgent и в публичной доке отдельной страницы по нему нет. <!-- last-verified: 2026-04-27 source: docs.dynatrace.com/docs/ingest-from/technology-support/application-software/go -->
- Для **PHP**. Через расширение PHP (Zend extension) — стандартный способ добавления функционала.
- Для **Ruby**. В отличие от Java/.NET/Node.js/Python OneAgent не имеет собственного нативного агента под Ruby — телеметрия с Ruby-приложения снимается через [OpenTelemetry SDK](https://docs.dynatrace.com/docs/ingest-from/technology-support/application-software/ruby) и отправляется в Dynatrace по OTLP-протоколу. <!-- last-verified: 2026-04-27 source: docs.dynatrace.com/docs/ingest-from/technology-support/application-software/ruby -->

Итог для команды приложения: **разработчик не пишет ни одной строчки дополнительного кода**, не меняет конфигурацию, не добавляет в проект библиотек. Поставил OneAgent, перезапустил приложение — Dynatrace уже видит каждый запрос.

#### Установка OneAgent в air-gapped среде

В нашем случае (изолированный кластер) установщик OneAgent скачивается напрямую с кластера:

```bash
# Linux
wget --no-check-certificate -O Dynatrace-OneAgent-Linux.sh \
  "https://<наш-кластер>/api/v1/deployment/installer/agent/unix/default/latest?Api-Token=<TOKEN>"
sudo /bin/sh Dynatrace-OneAgent-Linux.sh

# Windows
Invoke-WebRequest -Uri "https://<наш-кластер>/api/v1/deployment/installer/agent/windows/default/latest?Api-Token=<TOKEN>" -OutFile Dynatrace-OneAgent.exe
.\Dynatrace-OneAgent.exe
```

Никаких обращений в интернет — установщик берётся с самого кластера. Это работает в полностью изолированной сети.

#### Управление обновлениями OneAgent

OneAgent умеет обновляться сам. По умолчанию — да, обновляется автоматически при появлении новой версии в кластере (а кластер получает новые версии админ через ручную загрузку). Это можно отключить (например, для критичных серверов, где любое изменение должно пройти change-management).

Управление обновлениями: **Settings → Deployment → OneAgent updates** (мы это посмотрим в теме «Компоненты системы»).

### Уровень 2 — ActiveGate (промежуточный шлюз)

ActiveGate — это отдельная программа-посредник между OneAgent и серверной частью кластера. Слово составное: *Active* (активный) + *Gate* (ворота, шлюз). Дословно — «активный шлюз»: не просто пропускает трафик, а ещё и обрабатывает его.

#### Три основные роли ActiveGate

**Роль 1 — шлюз связи (communication gateway).**
Если у клиента сотни серверов с OneAgent (для иллюстрации возьмём 500 — в крупных банках это типичный масштаб) <!-- qc:ignore=FAKE_SUCCESS_STORY -->, не нужно, чтобы каждый из них пытался напрямую достучаться до кластера Dynatrace. Все они отправляют данные в ActiveGate, ActiveGate их сжимает и одним потоком пересылает на кластер. Это сильно снижает нагрузку на сеть и упрощает настройку межсетевого экрана: порт открывается только из ActiveGate в кластер, а не из каждого OneAgent.

ActiveGate применяет сжатие и батчинг перед отправкой в кластер — уменьшает исходящий объём и число соединений. Точный коэффициент зависит от природы трафика (логи жмутся сильно, уже сжатые метрики — слабее), но эффект всегда ощутимый и специально оптимизируется для air-gapped контуров, где каждый мегабайт проходит через шлюз.

**Роль 2 — сборщик данных извне (data ingestion).**
OneAgent можно поставить только на сервер с поддерживаемой ОС. Но мониторить нужно и то, на что агент не ставится:

- **Сетевые коммутаторы и маршрутизаторы** (Cisco, Juniper, Huawei). Это «железные коробки» с прошивкой, на них нельзя установить программу.
- **Системы хранения данных (СХД)** — физические массивы дисков с собственным управляющим контроллером.
- **Специализированные приложения** без официальной поддержки (например, тяжёлый legacy-софт на Cobol или 1С с особыми требованиями).
- **Базы данных через JDBC** — особенно полезно для Oracle, MS SQL, PostgreSQL, где нужны метрики на уровне SQL (top queries, deadlocks, replication lag).

Для всех этих случаев ActiveGate использует **расширения** (extensions) — специальные плагины, которые опрашивают внешние системы по их собственным протоколам:

- **SNMP** (Simple Network Management Protocol — простой протокол сетевого управления) — стандартный протокол для опроса сетевого оборудования. Версии: SNMPv1, v2c, v3 (последняя поддерживает аутентификацию и шифрование).
- **JDBC** (Java Database Connectivity — соединение Java с базами данных) — подключается к базам данных и выполняет SQL-запросы для снятия метрик.
- **VMware vCenter API** — программный интерфейс к серверу управления VMware, отдаёт данные о виртуальных машинах, хостах, datastore.
- **Prometheus scraping** — забирает метрики с эндпоинтов в формате Prometheus.
- **HTTP/REST** — кастомные плагины могут опрашивать любой HTTP-endpoint.

В air-gapped среде расширения **устанавливаются как файлы** — администратор скачивает .zip из портала Dynatrace на отдельной машине с интернетом, переносит на USB или через шлюз обмена в изолированную сеть, и загружает через UI кластера в **Hub → Manage extensions**.

**Роль 3 — запуск синтетических проверок.**
Synthetic monitoring — это эмуляция действий пользователя по расписанию. Например, каждые 5 минут проверять, что страница логина в интернет-банке открывается за 2 секунды. Эти проверки запускаются с ActiveGate, потому что нужен исполнитель внутри сети клиента (часто проверяемая система не доступна из интернета).

Два типа синтетики:
- **HTTP monitor** — простой HTTP-запрос на URL с проверкой статуса и времени отклика.
- **Browser monitor** — полноценный браузер (на базе Chromium) выполняет сценарий: открыл страницу, ввёл логин, нажал кнопку, проверил что появился элемент.

Browser monitor требует отдельной роли ActiveGate с достаточным CPU и памятью.

#### Два типа ActiveGate в Managed

**Cluster ActiveGate** — встроенный в кластер. Один на весь кластер, минимально нужен. Принимает данные от OneAgent (если нет Environment ActiveGate между ними) и от других Environment ActiveGate.

**Environment ActiveGate** — отдельный, ставится в подсетях клиента ближе к мониторируемым системам. Может быть несколько штук:
- Один в продакшн-зоне
- Один в DMZ (демилитаризованная зона — изолированная подсеть с публично доступными сервисами)
- Один на удалённой площадке (филиал в другом городе)
- Один для синтетики
- Один с extensions (SNMP, JDBC, ...)

В реальном проекте обычно ставят 2–4 Environment ActiveGate для распределения нагрузки и резервирования.

#### Минимальные требования к серверу под ActiveGate

**Абсолютный минимум** для standalone Linux ActiveGate (источник: `docs.dynatrace.com/docs/ingest-from/dynatrace-activegate/installation/linux/linux-activegate-hardware-and-system-requirements`):

- **2 ГБ RAM** (рекомендуется 4 ГБ)
- **1 двухъядерный процессор**
- **4 ГБ** свободного диска под установку, конфигурации и логи + **4 ГБ** под кэш установщиков и контейнер-образов + **~2 ГБ** под логи Extension Controller

Сверх этого в той же документации Dynatrace приводит **sizing guide** по типу инстанса (для x86-64 на примере AWS-class instances) с указанием числа OneAgent, которое ActiveGate сможет обслужить:

| Тип | vCPU | RAM | OneAgent за ActiveGate |
|---|---|---|---|
| Малый (~c6i.large) | 2 | ~4 ГБ | ~800 |
| Средний (~c6i.xlarge) | 4 | ~8 ГБ | ~1 800 |
| Большой (~c6i.2xlarge) | 8 | ~15 ГБ | ~2 500 |

Для ARM-архитектуры (AArch64) та же пропускная способность достигается на меньшем ресурсе. Цифры ориентировочные — для air-gapped Managed и подключённых тяжёлых модулей (synthetic, extensions) расход может быть выше. В production делайте запас и сверяйтесь с актуальной матрицей в docs для вашей версии Dynatrace.

Для Browser-синтетики ресурсы подбираются отдельно — браузерные сессии тяжелее HTTP-проб, RAM и ядер нужно ощутимо больше в зависимости от числа параллельных тестов (источник: `docs.dynatrace.com/docs/observe/digital-experience/synthetic-monitoring/private-synthetic-locations/system-and-hardware-requirements-for-private-synthetic`).

### Уровень 3 — Серверная часть (Managed Cluster)

Это «мозг» системы. Серверная часть — это **кластер из узлов** (по-английски *nodes*), которые клиент разворачивает на своих виртуальных машинах. Минимально нужен один узел, для боевой установки рекомендуется три узла. Три — для отказоустойчивости: если один упадёт, два оставшихся продолжат работать.

#### Программные компоненты каждого узла

| Компонент | Что делает |
|---|---|
| **Server** | Принимает данные от OneAgent и ActiveGate, нормализует, передаёт другим компонентам, генерирует UI |
| **Cassandra** | База данных типа NoSQL (без жёсткой схемы таблиц), рассчитанная на миллиарды записей. Хранит метрики и конфигурации годами. Apache-проект |
| **Elasticsearch** | Поисковый движок. Индексирует логи, тексты ошибок, описания объектов мониторинга, чтобы поиск работал за миллисекунды |
| **Davis AI** | Движок искусственного интеллекта. Анализирует все метрики в реальном времени, строит базовые линии, находит аномалии, создаёт инциденты (Problems) |
| **NGINX** | Веб-сервер для UI и API |

#### Cluster Management Console (CMC)

CMC — это **отдельный веб-интерфейс для администрирования кластера**, не путать с основным интерфейсом мониторинга. По умолчанию открывается на порту 8021 (адрес вида `https://<кластер>:8021/cmc`). В CMC администратор:

- Добавляет и убирает узлы
- Управляет лицензиями (сколько Host Units куплено, сколько использовано)
- Делает резервные копии и восстановление
- **Загружает обновления Dynatrace из заранее скачанных пакетов** (см. Часть 5)
- Настраивает SMTP для отправки писем (обычно используется внутренний SMTP-сервер банка)
- Настраивает интеграцию с LDAP/SAML/OIDC

CMC обычно доступен только администратору кластера и нескольким DevOps-инженерам — отдельная учётка с расширенными правами.

## 🎓 Часть 3. Поток данных и сетевые требования

### Как данные путешествуют от приложения до интерфейса

```
[Приложение Java на сервере app01]
         ↓ (OneAgent встраивает датчики в код)
[OneAgent на app01]
         ↓ (HTTPS, порт 443, сжатый трафик)
[Environment ActiveGate в подсети DMZ]
         ↓ (HTTPS, порт 443)
[Cluster ActiveGate в кластере]
         ↓ (внутрикластерная связь)
[Компонент Server кластера]
         ↓ (распределяет данные)
[Cassandra (хранение) + Elasticsearch (поиск) + Davis AI (анализ)]
         ↑ (читает накопленные данные)
[Веб-интерфейс кластера] ← пользователь открывает в браузере
```

**Время от события до отображения в интерфейсе:** обычно 5–15 секунд. OneAgent отправляет данные не каждое событие отдельно, а пакетами раз в 10 секунд (это называется **batch-передача** — от англ. *batch* = «партия»).

### Сетевые порты и направление соединений

Главное правило для безопасника. Все соединения **инициируются изнутри**: OneAgent сам стучится в ActiveGate, ActiveGate — в Cluster. Снаружи в сеть клиента для передачи телеметрии ничего не входит.

| Источник | Назначение | Порт | Протокол | Зачем |
|---|---|---|---|---|
| OneAgent | Environment ActiveGate | 9999 (по умолчанию) или 443 | HTTPS | Отправка данных мониторинга |
| OneAgent | Cluster (если без AG) | 443 | HTTPS | Прямое подключение к кластеру |
| Environment ActiveGate | Cluster ActiveGate | 443 или 8443 | HTTPS | Передача данных и метаданных |
| Браузер пользователя | Cluster (UI) | 443 | HTTPS | Веб-интерфейс |
| Администратор | CMC | 8021 | HTTPS | Cluster Management Console |
| Cluster ⇆ Cluster (multi-node) | Внутри | 9091, 9100, 9300, 7001 и др. | TCP | Внутрикластерная синхронизация Cassandra и Elasticsearch |

**По работе с файрволом.** Входящих соединений в сеть клиента для передачи телеметрии нет. Единственный входящий трафик — соединения администратора и пользователей Dynatrace UI на порт 443. Телеметрия всегда идёт исходящими соединениями: OneAgent подключается к ActiveGate на 443, ActiveGate — к Cluster на 443. Интернет для работы кластера не требуется — установка работает полностью в изолированном контуре.

### TLS и сертификаты

Все соединения зашифрованы по TLS (Transport Layer Security — протокол защиты соединения, ранее назывался SSL).

**По умолчанию** Dynatrace использует самоподписанные сертификаты. Это работает, но при подключении OneAgent к ActiveGate нужно вручную доверять сертификату.

**Для production** в банках обычно ставят **корпоративные сертификаты от внутреннего CA** (Certificate Authority — центр сертификации). Это:
- Серверный сертификат для UI кластера
- Серверный сертификат для CMC
- Серверный сертификат для каждого ActiveGate
- Подписанные одним корневым корпоративным CA

После установки корневой сертификат CA должен быть в truststore (хранилище доверенных сертификатов) на каждом хосте OneAgent и каждом ActiveGate.

Самая частая проблема первого подключения: **TLS handshake failure** между OneAgent и ActiveGate. Решается импортом корневого сертификата в truststore на хосте OneAgent.

## 🎓 Часть 4. Безопасность и аутентификация

### Аутентификация пользователей в Dynatrace Managed

Dynatrace Managed поддерживает несколько способов входа пользователей:

**1. Локальные учётные записи.** Пользователи и пароли хранятся внутри кластера. Подходит для administrator-аккаунта восстановления, но в банках основные учётки локально не делают — все через корпоративный AD.

**2. LDAP/Active Directory.** Подключение к корпоративному каталогу пользователей. Самый частый вариант в банках. Настраивается через CMC. Поддерживает группы — можно мапить AD-группы на Dynatrace-роли. После настройки сотрудник заходит в Dynatrace своим обычным корпоративным логином.

**3. SAML 2.0.** Single Sign-On (единый вход) через корпоративный Identity Provider — Microsoft ADFS, Keycloak, Okta. SAML — это XML-стандарт обмена данными аутентификации.

**4. OpenID Connect (OIDC).** Современная альтернатива SAML, на основе OAuth 2.0. Поддержка в Managed появилась позднее, чем SAML/LDAP — конкретный минимально требуемый номер сборки в публичной документации Dynatrace явно не зафиксирован, поэтому при планировании внедрения OIDC в air-gapped Managed уточняется по release notes текущей версии и матрице совместимости вашего IdP.

При использовании SAML/OIDC локальные пароли можно отключить совсем — вход возможен только через корпоративный SSO.

### RBAC — управление правами

RBAC (Role-Based Access Control — управление доступом на основе ролей) — модель, где у пользователя нет прав напрямую, а есть **роли**, которые дают права.

**Встроенные роли в Dynatrace:**

| Роль | Что разрешает |
|---|---|
| **Viewer** | Только просмотр — дашборды, метрики, трейсы, проблемы |
| **User (Manage settings)** | Просмотр + изменение settings своего environment'а |
| **Configure cluster** | Управление узлами, лицензиями, обновлениями |
| **Cluster admin** | Полный доступ ко всему |
| **Audit log viewer** | Только просмотр audit-логов |

В Managed на каждый environment (а в кластере может быть несколько окружений — например, prod и dev) настраиваются свои наборы пользователей с разными ролями.

### Management Zones — сегментация данных

Management Zone (зона управления) — это правило, по которому данные мониторинга разбиваются на «куски». Каждой команде даётся доступ только к своим куском.

**Пример банка:**
- У клиента три ИТ-команды: фронтенд (интернет-банк), бэкенд (АБС-системы), инфраструктура
- Создаются три Management Zone: `Internet Bank`, `Core Banking`, `Infrastructure`
- Правила: «всё с тегом `team=front` → MZ Internet Bank», и т.д.
- Пользователю фронтенда даётся доступ только к MZ Internet Bank — он видит только свои приложения, на дашбордах и в Problems

В крупных организациях без Management Zones один администратор Dynatrace оказывается единственным человеком, видящим мониторинг всей компании — риск и с точки зрения безопасности, и с точки зрения нагрузки на одного сотрудника.

Настройка: **Settings → Preferences → Management zones**.

### Audit log

Все действия пользователей в Dynatrace логируются в audit log:
- Кто и когда вошёл
- Кто что менял в Settings
- Кто открывал какие токены API

Просмотр: **Manage → Audit log** в Managed (требует роль Audit log viewer).
По официальной странице [Audit logs via API](https://docs.dynatrace.com/docs/manage/data-privacy-and-security/configuration/audit-logs-api) Dynatrace **хранит audit-логи 30 дней** и автоматически удаляет их по истечении срока. Если контур требует более длительного хранения (compliance, СБ, SIEM-аудит), типовая практика в банке — настроить выгрузку в корпоративную SIEM (Security Information and Event Management) сразу после генерации, а в самом Dynatrace опираться на стандартные 30 дней. <!-- last-verified: 2026-04-27 source: docs.dynatrace.com/docs/manage/data-privacy-and-security/configuration/audit-logs-api -->

## 🎓 Часть 5. Обновления Dynatrace в air-gapped среде

В изолированной сети **обычная схема обновлений через Mission Control недоступна** — отсюда отдельный процесс ручной загрузки пакетов, описанный ниже.

### Обычная (cloud-connected) схема — НЕ для нас

Если бы кластер был подключён к интернету, работало бы так:
- Кластер периодически обращается в облачный сервис **Mission Control**
- Mission Control сообщает о доступных обновлениях
- Кластер сам качает пакет и применяет обновление

В нашем кейсе **этого нет** — кластер изолирован, к Mission Control не подключается.

### Air-gapped схема обновлений — наш вариант

Процесс выглядит так:

**Шаг 1. Администратор скачивает пакет обновления.**
С отдельной машины, имеющей доступ в интернет, администратор заходит в **Dynatrace customer portal** (`https://customers.dynatrace.com`). Там доступен раздел загрузок — все версии обновлений за всё время поддержки контракта.

Качается **полный пакет обновления** для нужной версии — архив включает:
- Серверные компоненты (Dynatrace server, Cassandra, Elasticsearch, NGINX)
- Версии OneAgent для всех поддерживаемых ОС
- Версии ActiveGate
- Файлы метаданных (signed manifest)
- Скрипты установки

**Шаг 2. Перенос в изолированную сеть.**
Файл переносится через утверждённый клиентом канал передачи данных в изолированную сеть. Варианты:
- **Шлюз обмена файлами** — отдельная машина-«куница» в DMZ с двусторонней проверкой контрольных сумм
- **USB-носитель** — у некоторых клиентов с самыми жёсткими требованиями
- **Корпоративный файловый сервер**, подключённый к обеим сетям с антивирусной проверкой

**Шаг 3. Загрузка в CMC.**
Администратор заходит в Cluster Management Console (`https://<кластер>:8021/cmc`), раздел **Cluster updates** или **Maintenance → Update**.

Там:
- Кнопка **Upload package** (загрузить пакет)
- Указание пути к скачанному .zip
- CMC проверяет цифровую подпись пакета
- Показывает summary — какая версия, что изменилось

**Шаг 4. Применение обновления.**
В CMC выбирается режим:
- **Apply now** — обновление применится сразу с rolling restart узлов
- **Schedule update window** — назначить на время обслуживания

При применении CMC автоматически:
1. Распаковывает пакет на кластере
2. По очереди обновляет каждый узел (rolling fashion — кластер не падает целиком)
3. Каждый узел перед перезагрузкой выводится из обслуживания
4. После обновления проводится health check
5. Если health check прошёл — следующий узел; если нет — обновление останавливается с алертом

**Шаг 5. Обновление OneAgent (отложенное).**
После обновления кластера в нём появляются новые версии OneAgent. Они становятся доступны для скачивания и для авто-обновления (если настроено). Сами хосты будут обновляться по своему расписанию.

### Типы обновлений

**Hot patches.** Маленькие исправления внутри одной минорной версии (например, `1.270.10 → 1.270.11`). Применяются без перезагрузки кластера, без даунтайма. В банках их применяют срочно при критических уязвимостях.

**Minor updates.** Обновления внутри major-версии (`1.270 → 1.271`). Обычно требуют rolling restart узлов — кластер не падает, но каждый узел по очереди перезагружается. Применяются раз в 1-2 месяца.

**Major upgrades.** Большие обновления (`1.260 → 1.270`). Раз в полгода. Требуют полного просмотра release notes, тестирования на dev-кластере, окна обслуживания. В банках обычно делают по плану, согласованному за 2–4 недели.

**Цикл выпуска от Dynatrace.** Dynatrace релизит платформу спринтами раз в две недели — для Managed это видно в [release notes Managed](https://docs.dynatrace.com/docs/whats-new/release-notes/managed) (рассылка `sprint-NNN`, версии 1.336 / 1.334 / 1.332 ...). Не каждый спринт автоматически попадает в air-gapped кластер: в Managed применяется в среднем каждый 4-й спринт, и сборка выкатывается клиентам через CMC. Терминов «LTS» / «ESM» в публичной документации Dynatrace на момент сверки нет — в air-gapped инсталляциях принято говорить просто о «принятой к промышленному применению версии» по согласованию с заказчиком. <!-- last-verified: 2026-04-27 source: docs.dynatrace.com/docs/whats-new/release-notes/managed -->

В CMC можно настроить **Update windows** — окна, в которые разрешено автообновление (например, «только в субботу с 2:00 до 5:00»).

### Best practices air-gapped обновлений

1. **Иметь 2 кластера** — production + staging. Обновлять сначала staging, ждать неделю, потом production.
2. **Хранить локально 2-3 предыдущих пакета** обновления — для возможности отката.
3. **Делать backup перед обновлением** через CMC — если что-то пойдёт не так, восстановление за 2-4 часа.
4. **Тщательно читать release notes** на customer portal — особенно секцию «Breaking changes».
5. **Согласовывать окно обслуживания** с владельцами критичных систем за 2 недели.
6. **Документировать процесс** загрузки пакета и переноса через шлюз — это часть compliance-аудита.

## 🎓 Часть 6. Кластерные топологии и High Availability

### Single-node кластер

Один узел. Подходит только для тестов и dev-окружений.

- Простой
- Дешёвый
- НЕТ отказоустойчивости — упал сервер, упал весь Dynatrace

### Multi-node кластер (рекомендованный для prod)

Три узла или больше. Все узлы идентичны — каждый содержит полный набор компонентов (Server + Cassandra + Elasticsearch + Davis).

**Как это работает:**
- Cassandra реплицирует данные между узлами с фактором репликации 3 (каждая запись хранится на трёх узлах)
- Elasticsearch использует свою схему primary+replica shards
- Если один узел падает — два оставшихся продолжают работу
- Если падает большинство (2 из 3) — кластер останавливается чтобы избежать split-brain (раздвоения данных)

**Минимум для production: 3 узла.** Меньше — нет отказоустойчивости. 5 узлов — для очень больших инсталляций.

### Multi-region (распределённый кластер)

Узлы в разных дата-центрах с low-latency связью между ними (< 10 ms ping).

Полезно когда:
- Один ДЦ — основной, второй — резервный
- Нужна катастрофоустойчивость на случай потери целого ДЦ

Требует **дорогой межДЦ связи** — Cassandra и Elasticsearch очень чувствительны к latency. Для большинства казахстанских банков с одним ДЦ это не нужно.

### Backup и Disaster Recovery

**Автоматические backup в CMC.** Кластер по умолчанию делает регулярные backup через Cluster Management Console — отдельно для конфигурации (хранится в Cassandra), данных мониторинга (Cassandra-таблицы метрик и трейсов) и индексов Elasticsearch. Точная частота и расписание задаются в CMC и зависят от размера кластера и подключённого хранилища; конкретные интервалы в публичных Managed-доках одной таблицей не зафиксированы — авторитетный источник на каждой инсталляции — экран **CMC → Backup**. На многих банковских кластерах конфигурация бэкапится несколько раз в сутки, данные и индексы — раз в сутки.

**Куда:**
- Локальный диск узла (по умолчанию — плохой вариант, потеряем при потере узла)
- NFS share на корпоративной СХД (рекомендуется)
- S3-совместимое объектное хранилище (MinIO, Ceph) — если есть в инфраструктуре банка

**Восстановление:**
- Из CMC, при инсталляции нового кластера, выбирается опция «Restore from backup»
- Время восстановления зависит от объёма данных: для 1 ТБ обычно 2–4 часа

**Disaster Recovery.** Backup и восстановление автоматизированы. RTO (Recovery Time Objective — целевое время восстановления) измеряется часами. RPO (Recovery Point Objective — целевая точка отката) составляет обычно не больше 4 часов потери конфигурации и 24 часов потери метрик. При наличии репликации backup на удалённую площадку DR-процедура гарантируется на уровне SLA.

## 🎓 Часть 7. Хранение данных, retention и сайзинг

### Retention — сколько данных хранится

В Managed работает **Classic-стек хранения** (Cassandra для метрик, Elasticsearch для логов и сессий, файловое хранилище для PurePath). Grail-хранилище с его возможностью гибкой настройки retention до 10 лет — это SaaS-only функциональность. Значения ниже взяты из официальной страницы [Data retention periods](https://docs.dynatrace.com/docs/shortlink/data-retention-periods) для Classic-направления и относятся к дефолтам закупленного аккаунта. <!-- last-verified: 2026-04-27 source: docs.dynatrace.com/docs/shortlink/data-retention-periods -->

| Тип данных | По умолчанию в Managed (Classic) | Примечание |
|---|---|---|
| **Трейсы (PurePath, Distributed traces Classic)** | 10 дней | В SaaS через Grail — configurable 10 дней — 10 лет. В Managed фиксировано. |
| **Метрики Classic** | до 5 лет с понижением гранулярности | Высокое разрешение (1 мин) хранится ограниченный период, далее данные агрегируются в 5/15-минутные и часовые ряды. Конкретные пороги проверяются в разделе retention docs для вашей версии. |
| **Логи (Log Monitoring Classic)** | 35 дней | В SaaS через Grail Log Management — configurable до 10 лет. В Managed стандартное окно — 35 дней. |
| **User sessions (RUM)** | 35 дней | Классический RUM. |
| **Session Replay** | 35 дней | Дольше не настраивается в Classic-стеке. |
| **Synthetic** | 35 дней | — |
| **Davis Problems и события** | 14 месяцев | Сами инциденты, не сырые данные. |
| **OneAgent diagnostics** | 30 дней | Диагностика агента (не метрики, а логи установки/апдейтов). |

**Аудит действий пользователей** в Managed хранится отдельно от основных данных и конфигурируется независимо — конкретный срок зависит от настроек вашего кластера и требований внутренней службы ИБ. Уточнять нужно в разделе Audit log администрирования.

Чем больше retention — тем больше нужно дисков. Это входит в сайзинг.

### Расширенный сайзинг

Для понимания масштаба и для пресейла (когда клиент спрашивает «сколько нам нужно железа») Dynatrace публикует матрицу типоразмеров узлов кластера. Размер выбирается по **максимальному числу Host Units (HU)** и **пиковому числу пользовательских действий в минуту**, которые узел способен обслужить. Значения ниже взяты из [Managed cluster — minimum hardware requirements](https://docs.dynatrace.com/managed/managed-cluster/installation/managed-hardware-requirements) и применяются на узел (в multi-node кластере все узлы идентичны). <!-- last-verified: 2026-04-27 source: docs.dynatrace.com/managed/managed-cluster/installation/managed-hardware-requirements -->

| Тип узла | Max HU | Пик действий/мин | vCPU | RAM | Disk IOPS |
|---|---|---|---|---|---|
| Micro | 50 | 1 000 | 4 | 32 ГБ | 500 |
| Small | 300 | 10 000 | 8 | 64 ГБ | 3 000 |
| Medium | 600 | 25 000 | 16 | 128 ГБ | 5 000 |
| Large | 1 250 | 50 000 | 32 | 256 ГБ | 7 500 |
| XLarge | 2 500 | 100 000 | 64 | 512 ГБ | 10 000 |

**Premium High Availability (multi-datacenter)** — отдельная таблица для геораспределённого кластера: Large = до 600 HU (32 vCPU / 256 ГБ), XLarge = до 1 250 HU (64 vCPU / 512 ГБ). В этом режиме суммарная ёмкость кластера ниже, потому что часть ресурсов уходит на межДЦ-репликацию.

**Ключевые требования к кластеру:**

- **Минимум 3 узла для production** — одноузловой кластер допускается только для dev/PoC и не отказоустойчив.
- **Все узлы должны иметь идентичную конфигурацию оборудования** — смешанные размеры недопустимы.
- **Log Monitoring включён** → минимум 64 ГБ RAM на всех узлах (даже если HU-лимит попадает в Micro).
- **Сетевая задержка между узлами — максимум 10 мс** (не только пропускная способность).
- **Пропускная способность сети между узлами:** 1 Гбит/с минимум, 10 Гбит/с рекомендуется.

Все перечисленные пороги — из той же страницы `docs.dynatrace.com/managed/managed-cluster/installation/managed-hardware-requirements`, раздел «Prerequisites and multi-node constraints».

**Пояснение типов дисков.** В требованиях выше указаны только IOPS — тип диска подбирается так, чтобы IOPS обеспечивались.

- **HDD** (Hard Disk Drive — жёсткий диск с вращающимися пластинами) — медленный, не подходит для Cassandra на любом размере.
- **SSD** (Solid State Drive — твердотельный накопитель на флэш-памяти) — подходит для Micro/Small/Medium.
- **NVMe** (Non-Volatile Memory Express — стандарт подключения SSD напрямую к шине PCIe) — для Large / XLarge, где IOPS ≥ 7 500 стабильно держать на обычном SSD сложно.

## 🎓 Часть 8. Лицензирование Managed

### Host Units (HU) — единицы хостов

HU рассчитывается по объёму памяти хоста, округлённому вверх к следующей ступени в 16 GiB (15.3 ГиБ):

- до **16 GiB** → **1 HU**
- **17–32 GiB** → **2 HU**
- **33–48 GiB** → **3 HU**
- и далее +1 HU на каждые следующие 16 GiB памяти

Формула зафиксирована в `docs.dynatrace.com/docs/shortlink/host-unit`: «когда объём RAM хоста попадает между значениями таблицы — число HU округляется вверх».

Отдельный режим — **Infrastructure Monitoring mode**: тарифицируется в разы дешевле Full-Stack, потому что OneAgent собирает только инфраструктурные метрики без глубокой инструментации процессов. В Managed точная доля HU для Infrastructure-режима зависит от памяти хоста и условий контракта — сверяться нужно с `docs.dynatrace.com` и условиями своего лицензионного соглашения.

### DDU (Davis Data Units) — единицы данных Davis

Лицензируется приём:
- Логов
- Бизнес-событий
- Кастомных метрик

Считается по объёму поглощённых данных: каждый тип (метрики, логи, события) имеет свой коэффициент расхода DDU за мегабайт. Актуальные коэффициенты — в условиях контракта и на странице `docs.dynatrace.com/docs/shortlink/davis-data-units`; на пилоте обязательно измеряется фактический расход DDU, чтобы правильно закупить объём.

### Synthetic actions

- **HTTP monitor execution** — 1 единица за каждое выполнение HTTP-запроса
- **Browser monitor step** — 1 единица за каждый шаг браузерного скрипта

Считается ежемесячно. Нужно следить — браузерные мониторы дороже.

### Application Security Units (ASU)

Если используется модуль **Application Security** (защита от уязвимостей и атак):
- Лицензируются по отдельной модели
- Считается по числу хостов с активным AppSec-мониторингом

### Real User Monitoring units

- **Web RUM session** — 1 единица за сессию пользователя сайта
- **Mobile RUM session** — 1 единица за сессию мобильного приложения

При большом трафике (миллионы сессий в месяц) — отдельная статья расходов.

### Управление лицензиями в air-gapped кластере

Лицензионный ключ загружается в CMC при первой установке. Срок действия задаётся условиями контракта, продление — до истечения ключа. Использование лимитов видно в **CMC → Licensing**:
- Сколько HU куплено / используется
- Сколько DDU за текущий месяц
- Сколько Synthetic actions за месяц

При приближении к лимиту — алерт в Dynatrace и уведомление администратору. Превышение лимитов не останавливает мониторинг сразу, но в долгосрок требуется докупить.

## 🎓 Часть 9. Расширения и REST API

### Архитектура расширений (Extensions)

Extensions — это плагины, расширяющие функциональность мониторинга.

**Два поколения extensions:**

**Extensions 1.0** (старое, deprecated с 2024).
Java или Python скрипты, которые выполняются на ActiveGate и опрашивают внешние системы. Например, плагин для мониторинга IBM MQ.

**Extensions 2.0** (рекомендованные).
Универсальный YAML-формат, поддерживает множество протоколов (SNMP, JMX, JDBC, WMI, SQL). Не требует программирования — настройка через файлы. Запускается на ActiveGate или прямо на OneAgent.

**Каталог:** Hub → Extensions. Сотни готовых для популярных систем (PostgreSQL, Oracle, Redis, Kafka, Cisco, Fortinet, F5, NetApp).

### Установка расширений в air-gapped среде

В отличие от cloud-варианта, **прямая установка из Hub-marketplace через интернет невозможна**. Процесс:

1. На машине с интернетом — открыть Dynatrace Hub в портале клиента, найти нужное расширение, скачать .zip
2. Перенести .zip в изолированную сеть (через шлюз обмена)
3. В Dynatrace UI клиента: **Hub → Manage extensions → + Upload extension**
4. Загрузить .zip
5. Расширение появляется в списке установленных, дальше настраивается как обычно

Управление: **Settings → Monitoring → Extensions**.

### REST API

У Dynatrace огромный набор REST API:
- **Configuration API** — чтение/изменение настроек (создание dashboard'ов программно, экспорт настроек)
- **Metrics API** — запросы метрик (для интеграции с внешними системами BI)
- **Problems API** — получение списка проблем (для интеграции с ITSM)
- **Synthetic API** — управление синтетическими мониторами
- **OneAgent API** — управление агентами

Аутентификация — **API tokens** (генерируются в **Settings → Integration → Dynatrace API**).

API очень богатый — практически весь UI можно автоматизировать через API. Все API доступны локально на кластере (`https://<кластер>/api/...`), никакого интернета не нужно.

## 🎓 Часть 10. Типичные проблемы инсталляции и эксплуатации

1. **TLS handshake failure** между OneAgent и ActiveGate. Решение: импорт корневого CA в truststore хоста.
2. **Cassandra disk I/O too slow** — поставили на HDD вместо SSD. Решение: переезд на SSD/NVMe.
3. **Out of memory на узлах** — недосайзинг кластера. Решение: добавить памяти узлам или добавить узлы.
4. **Backup не настроен** — после первого сбоя клиент теряет данные. Решение: включить backup в CMC сразу после инсталляции.
5. **OneAgent не определяет процесс приложения** — обычно это нестандартный путь к JVM или нестандартные параметры запуска. Решение: проверить supported technologies, добавить в Process Detection Rules.
6. **Лимит лицензий превышен** — кончились HU. Решение: либо докупить, либо снять OneAgent с менее важных хостов.
7. **Обновление застряло** — не хватило места на диске или сетевая проблема между узлами. Решение: проверить логи в CMC, при необходимости откатить через backup.
8. **Расширение не работает после загрузки** — несовместимая версия. Решение: проверить совместимость с версией Dynatrace в release notes расширения.

## 🎓 Часть 11. Пошаговая установка кластера Dynatrace Managed

Полный сценарий установки нового кластера на изолированной площадке.

### Подготовка инфраструктуры

**Сервера для узлов кластера** (минимум 3 для production):
- Виртуальные машины на VMware / Hyper-V / KVM
- Сетевая связность между узлами по 10 Гбит/с (сеть между узлами: ≤10 мс задержка, см. `docs.dynatrace.com/managed/managed-cluster/installation/managed-hardware-requirements`)
- Все узлы в одном vLAN или с минимальной задержкой между ними
- Одинаковая конфигурация (CPU, RAM, диск) — кластер требует симметричных узлов
- Хосты только под Dynatrace, ничего больше

**Операционная система:**
- RHEL 8/9, CentOS Stream 8/9, Rocky Linux 8/9, Alma Linux 8/9
- Или Ubuntu 22.04 LTS
- В банках и госорганизациях — сертифицированная Linux-сборка, утверждённая национальным регулятором (конкретный дистрибутив проверяется в матрице совместимости Dynatrace)

**Сетевые требования между узлами:**
- Открыты внутренние порты Cassandra: 7000, 7001, 9042
- Порты Elasticsearch: 9200, 9300
- Порты Server: 8021, 8443, 9091
- Порт NGINX: 443

**Дисковая конфигурация на каждом узле:**
- `/` (корень) — 50 ГБ (для ОС и Dynatrace бинарников)
- `/var/opt/dynatrace-managed` — основные данные. Минимум 500 ГБ NVMe для малых, 4 ТБ для больших
- `/var/lib/dynatrace-managed/elasticsearch` — индексы, отдельный том минимум 500 ГБ
- `/mnt/backup` — NFS share или отдельный диск для бэкапов

### Шаг 1. Скачивание установщика

На машине с интернетом, через Dynatrace customer portal:

1. Войти в `https://customers.dynatrace.com`
2. Раздел Downloads → Dynatrace Managed Installer
3. Выбрать версию (обычно последний LTS — Long Term Support, поддерживается дольше)
4. Скачать файл вида `dynatrace-managed-installer.sh` (около 2 ГБ)

### Шаг 2. Перенос установщика в изолированную сеть

Через утверждённый клиентом канал передачи данных:
- Шлюз обмена с антивирусной проверкой
- Или USB с разрешением безопасника

Сверить SHA-256 контрольную сумму после переноса.

### Шаг 3. Установка на первом узле

```bash
# На первом узле (под root):
chmod +x dynatrace-managed-installer.sh
sudo ./dynatrace-managed-installer.sh \
  --install-dir=/opt/dynatrace-managed \
  --data-dir=/var/opt/dynatrace-managed \
  --backup-dir=/mnt/backup
```

Установщик задаст вопросы:
- **Cluster IP** — внутренний IP узла
- **Public DNS name** — DNS-имя кластера для UI (например, `dynatrace.bank.kz`)
- **Cluster passphrase** — пароль для добавления новых узлов в кластер (запиши в безопасное место)
- **Initial admin password** — пароль для первичного входа в CMC

После установки — проверка:

```bash
sudo systemctl status dynatrace.target
# Должны быть зелёными: dynatrace-cassandra, dynatrace-elasticsearch, dynatrace-server, dynatrace-nginx
```

### Шаг 4. Первый вход в CMC

Открой в браузере: `https://<DNS-имя-кластера>:8021/cmc`

Войди под initial admin. Сразу после входа:
1. **Загрузить лицензионный файл** (.lic, скачивается с customer portal)
2. **Сменить admin password**
3. **Создать первого пользователя** с правами Cluster admin (свою личную учётку)

### Шаг 5. Добавление дополнительных узлов

На втором и третьем узле — тот же установщик, но в режиме «join»:

```bash
sudo ./dynatrace-managed-installer.sh \
  --cluster-node-ip=<IP-первого-узла> \
  --cluster-passphrase=<тот-самый-пароль>
```

Установщик автоматически синхронизирует Cassandra и Elasticsearch с первым узлом. Время — 30-60 минут на первичную репликацию данных.

### Шаг 6. Создание первого environment

В CMC → **Environments → + Create environment**:
- Название (например, `production`)
- Время удержания данных (retention)
- Лимиты использования

После создания — environment получит свой URL вида `https://<кластер>/e/<environment-id>/`.

### Шаг 7. Базовые проверки

- В CMC → **Cluster overview** — все узлы должны быть зелёными (Healthy)
- В Environment UI → **Settings → Notifications** — настроить хотя бы одну email-интеграцию для алертов о состоянии самого кластера
- В CMC → **Backup & restore** — включить и проверить, что первый автобэкап прошёл

## 🎓 Часть 12. Пошаговая установка OneAgent для разных операционных систем

После того как кластер работает, начинается развёртывание OneAgent на хосты.

### Получение установщика

Установщик OneAgent **не приходит как отдельный файл** — он встроен в кластер. Получить можно двумя способами:

**Способ 1 — через UI:**
1. Войти в Environment UI
2. **Manage → Deploy Dynatrace → Start installation**
3. Выбрать ОС (Linux / Windows / AIX / Solaris / z/OS)
4. Скопировать сгенерированную команду установки (она содержит правильный URL и токен)

**Способ 2 — через REST API** (для автоматизации):

```bash
curl -o Dynatrace-OneAgent-Linux.sh \
  "https://<кластер>/e/<env-id>/api/v1/deployment/installer/agent/unix/default/latest?Api-Token=<TOKEN>"
```

### Установка на Linux (RHEL, Ubuntu, Astra)

```bash
# Шаг 1. Скачать установщик (см. выше)
chmod +x Dynatrace-OneAgent-Linux.sh

# Шаг 2. Запустить установку
sudo /bin/sh Dynatrace-OneAgent-Linux.sh \
  --set-app-log-content-access=true \
  --set-host-group=production-banking \
  --set-infra-only=false
```

**Параметры:**
- `--set-app-log-content-access=true` — разрешить чтение логов приложений (нужно для Log Monitoring)
- `--set-host-group=...` — пометить хост группой (используется в Management Zones)
- `--set-infra-only=false` — собирать не только инфра-метрики, но и трейсы приложений

**Перезапуск приложений:**
- Java: достаточно остановить-запустить JVM (систем-юнит)
- .NET: то же самое для службы
- Node.js: рестарт процесса
- Без рестарта приложения OneAgent видит только метрики ОС, но не трейсы

### Установка на Windows Server

```powershell
# Шаг 1. Скачать установщик
Invoke-WebRequest -Uri "https://<кластер>/e/<env-id>/api/v1/deployment/installer/agent/windows/default/latest?Api-Token=<TOKEN>" -OutFile Dynatrace-OneAgent.exe

# Шаг 2. Установка (silent режим)
.\Dynatrace-OneAgent.exe /quiet `
  HOST_GROUP=production-banking `
  APP_LOG_CONTENT_ACCESS=true
```

**Особенности Windows:**
- Требуется перезагрузка Windows для активации OneAgent
- Антивирусы (Kaspersky, Symantec) могут блокировать инструментацию — добавить процессы Dynatrace в исключения

### Установка на AIX (для мейнфрейм-ориентированных банков)

```bash
gunzip Dynatrace-OneAgent-AIX.tar.gz
tar -xvf Dynatrace-OneAgent-AIX.tar
sudo /bin/sh dynatrace-oneagent-installer.sh
```

AIX поддерживается, но обновления выходят с задержкой 1-2 недели после Linux версий.

### Массовая установка через Ansible

Для развёртывания на 100+ хостах сразу — Ansible playbook:

```yaml
- name: Install Dynatrace OneAgent
  hosts: production
  become: true
  tasks:
    - name: Download installer
      get_url:
        url: "https://{{ dynatrace_cluster }}/e/{{ env_id }}/api/v1/deployment/installer/agent/unix/default/latest?Api-Token={{ api_token }}"
        dest: /tmp/oneagent.sh
        mode: '0755'
        validate_certs: no

    - name: Install OneAgent
      command: /bin/sh /tmp/oneagent.sh --set-app-log-content-access=true --set-host-group={{ host_group }}
      args:
        creates: /opt/dynatrace/oneagent/agent/conf/deploymentconf.conf
```

В банках обычно есть свой Ansible (или аналогичная система — Puppet, Chef, SaltStack), интеграция типовая.

### Проверка работы OneAgent

После установки на хосте:

```bash
# Проверить что демон запущен
sudo systemctl status oneagent

# Проверить статус подключения к кластеру
sudo /opt/dynatrace/oneagent/agent/tools/oneagentctl --get-config

# Логи OneAgent
sudo tail -f /var/log/dynatrace/oneagent/agent/oneagent.log
```

В UI Dynatrace → **Manage → Deployment Status** — новый хост должен появиться в течение 2-3 минут после установки.

## 🎓 Часть 13. Пошаговая установка ActiveGate

ActiveGate ставится отдельно от OneAgent — это самостоятельный сервер.

### Подготовка сервера под ActiveGate

- VM с Ubuntu / RHEL
- Минимум 4 ГБ RAM, 2 ядра, 32 ГБ диска (для боевой нагрузки подбирается по sizing guide: `docs.dynatrace.com/docs/ingest-from/dynatrace-activegate/installation/linux/linux-activegate-hardware-and-system-requirements`; короткая справка — в Части 2 выше)
- Сетевая связность до Cluster (порт 443) и до мониторируемых систем

### Скачивание установщика

В Environment UI → **Manage → Deploy Dynatrace → Install ActiveGate**:
- Выбрать тип: **Environment ActiveGate**
- Выбрать назначение: универсальный / synthetic / extensions
- Скопировать команду установки

```bash
wget --no-check-certificate -O Dynatrace-ActiveGate-Linux.sh \
  "https://<кластер>/api/v2/activeGates/installer/unix/default/latest?download&arch=x86&flavor=default&...&Api-Token=<TOKEN>"
```

### Установка

```bash
chmod +x Dynatrace-ActiveGate-Linux.sh
sudo /bin/sh Dynatrace-ActiveGate-Linux.sh
```

Установщик зарегистрирует ActiveGate в кластере. После завершения проверка:

```bash
sudo systemctl status dynatracegateway
```

### Настройка ActiveGate

После установки в UI: **Settings → Cluster ActiveGates** или **Settings → Environment ActiveGates** — настройка ролей.

Стандартные роли:
- **Routing** (включено по умолчанию) — приём данных от OneAgent, передача в кластер
- **Monitoring extensions** — для запуска плагинов
- **Synthetic monitoring** — для запуска синтетических проверок
- **Beacon forwarder** — для передачи RUM-бакон-сообщений

Для каждой включённой роли добавляются модули — в файле `/var/lib/dynatrace/gateway/config/custom.properties`:

```properties
# Включить SNMP-расширения
[com.compuware.apm.activegate.modules]
collectorMonitoring=true
extensions_v2=true

# Прокси для внешних соединений (если нужен)
[http.client.proxy]
http-proxy-server=proxy.bank.local
http-proxy-port=3128
```

После изменений — рестарт:
```bash
sudo systemctl restart dynatracegateway
```

### Перенаправление OneAgent на новый ActiveGate

После того как ActiveGate готов, OneAgent можно настроить отправлять данные через него:

```bash
sudo /opt/dynatrace/oneagent/agent/tools/oneagentctl --set-server=https://<ActiveGate-IP>:9999
sudo systemctl restart oneagent
```

## 🎓 Часть 14. Самомониторинг кластера Dynatrace

Кто мониторит сам Dynatrace. Dynatrace мониторит себя — встроенным механизмом Self-monitoring. Отдельный продукт для этого не нужен.

### Health страница в CMC

`https://<кластер>:8021/cmc` → **Cluster overview** → **Health**.

Что видно:
- Статус каждого узла (Healthy / Warning / Critical)
- Загрузка дисков на каждом узле
- Cassandra Heap usage и compaction queue
- Elasticsearch индексы и shard status
- Server connections и queue размеры
- Davis AI compute time

При проблеме — алерт в email + жёлтая/красная индикация на Health странице.

### Self-monitoring environment

В каждом кластере автоматически создаётся специальный environment под названием `Cluster monitoring`. В нём:
- Хосты узлов кластера
- Метрики самого Dynatrace
- Дашборд Cluster overview с готовыми визуализациями

Войти в этот environment под cluster admin: `https://<кластер>:8021/me/clusterhealth/`.

### Ключевые метрики для мониторинга

| Метрика | Норма | Что значит превышение |
|---|---|---|
| Cassandra heap usage | < 75% | Нужно увеличить heap или добавить узлы |
| Elasticsearch heap | < 75% | То же |
| Cassandra compaction pending | < 100 | Cassandra не успевает уплотнять данные — медленные диски |
| Disk usage | < 80% | Срочно добавить диск или сократить retention |
| Server response queue | < 1000 | Кластер не успевает обрабатывать данные |
| Davis compute lag | < 1 минута | Davis отстаёт от реального времени |
| Backup status | OK | Если Failed — данные не бэкапятся |

### Алерты о состоянии кластера

В CMC → **Settings → Cluster notifications** настраиваются:
- Кому слать (email, веб-хук)
- Какие события (узел упал, диск полон, backup провалился, лицензия близка к лимиту)
- На каком языке

Эти алерты идут отдельно от обычных Problems — их видит только администратор кластера, не пользователи.

### Логи самого Dynatrace

Если что-то сломалось — логи смотрим в:

```bash
# Логи Server-компонента
sudo tail -f /var/log/dynatrace/server/server.0.0.log

# Логи Cassandra
sudo tail -f /var/log/dynatrace/cassandra/system.log

# Логи Elasticsearch
sudo tail -f /var/log/dynatrace/elasticsearch/dynatrace.log

# Логи NGINX
sudo tail -f /var/log/dynatrace/nginx/error.log

# Логи установщика и обновлений
sudo tail -f /var/log/dynatrace/installer/installer.log
```

Эти логи — первая точка, куда смотрит администратор при диагностике проблем с самой платформой.

## 🎓 Часть 15. Multi-environment management — много окружений в одном кластере

Один кластер Dynatrace может содержать **несколько изолированных environments**. Каждый environment — это:
- Свой URL (`https://<кластер>/e/<env-id>/`)
- Свои пользователи и права
- Свои настройки
- Свои метрики и инциденты
- Своя лицензионная квота

### Зачем разделять на environments

**Сценарий 1 — Production / Staging / Dev.**
Каждое окружение в своём environment. Нет риска, что dev-настройки повлияют на production. Разные лимиты на retention.

**Сценарий 2 — Разделение по дочерним компаниям.**
В холдинге несколько банков. Каждый — свой environment. Каждый — своя команда DBA, разработчиков, безопасности с доступом только к своему.

**Сценарий 3 — Мульти-арендность для MSP** (Managed Service Provider — компания, которая обслуживает несколько клиентов).
Один MSP-партнёр обслуживает 10 клиентов. Каждый клиент — свой environment. Биллинг по environment.

### Создание нового environment

В CMC → **Environments → + Create environment**:
- **Name** — имя окружения
- **Quota** — лицензионный лимит (HU, DDU, Synthetic) — нельзя превысить общий лимит кластера
- **Retention settings** — сколько данных хранится
- **Initial admin user** — первый пользователь окружения

После создания — окружение получает URL и его можно сразу использовать.

### Лицензирование multi-environment

- Общая лицензия кластера (купленные HU) распределяется между environments
- Можно перераспределять в любое время через CMC
- Например: купили 500 HU → дали Production 400, Dev 50, Staging 50 <!-- qc:ignore=NO_SOURCE --> (цифры — иллюстрация распределения, не требование)

### Cross-environment функциональность

Между environments **нет общих данных** — каждое окружение полностью изолировано. Но в CMC видна агрегированная статистика по всем.

Для администрирования:
- Cluster admin видит ВСЕ environments
- Environment-specific user видит только свой environment

## 🎓 Часть 16. Типовые архитектурные шаблоны

В этом разделе — типовые шаблоны инсталляции Dynatrace Managed, которые собираются у заказчиков РК разной величины. Это не описание конкретного проекта и не маркетинговые кейсы — иллюстративные шаблоны, на которые можно опираться при проектировании собственного кластера. Конкретные цифры серверов, ActiveGate и лицензий всегда считаются по фактическому ландшафту заказчика.

### Шаблон 1 — Крупный банк с air-gapped контуром

**Ландшафт:** несколько сотен хостов, десятки прикладных сервисов, разделение на `prod` / `dev` / `DMZ` / синтетика. Предыдущее APM-решение заказчик мог не использовать вовсе либо мигрировать с другого продукта — на архитектуру кластера это не влияет.

**Архитектурный шаблон:**
- Multi-node Managed-кластер (минимум 3 узла для HA; размер подбирается по HU-лицензии и объёму трафика).
- Отдельные Environment ActiveGate под каждую изолированную сеть: production, non-production, DMZ, ActiveGate под Synthetic.
- OneAgent на все хосты с прикладной нагрузкой; для хостов БД — OneAgent + соответствующие технологии в Process group monitoring.
- Air-gapped инсталляция: обновления кластера, OneAgent и расширений приходят в виде пакетов, загружаемых через Cluster Management Console.

**Параллельная работа при миграции.** Если у заказчика есть действующее APM-решение, новый мониторинг запускается рядом — на период миграции дашбордов, алертов и runbook'ов. После переноса всех рабочих процессов старое решение выводится из эксплуатации.

### Шаблон 2 — Государственный сервис с требованием национального регулятора

**Ландшафт:** требования национального регулятора к локализации данных, сертифицированной ОС, аудиту действий пользователей.

**Архитектурный шаблон:**
- Кластер на Linux-сборке, сертифицированной национальным регулятором (конкретный дистрибутив — из матрицы совместимости Dynatrace).
- Полностью air-gapped: обновления через шлюз с антивирусной проверкой.
- Аудит-лог активности пользователей — с выгрузкой в корпоративный SIEM.
- Аутентификация через корпоративный SSO (LDAP / SAML) + обязательный MFA.
- Management Zones для разграничения видимости по департаментам.

**Особенности эксплуатации:**
- Каждое обновление Dynatrace проходит внутренний security review до загрузки в кластер.
- API-токены с правом на запись выдаются ограниченному кругу учётных записей.
- Резервные копии — на физически отделённое хранилище.

### Шаблон 3 — Телеком, multi-environment в одном кластере

**Ландшафт:** организация с несколькими территориальными подразделениями, в каждом — своя команда, работающая с собственным контуром систем. Центральной службе нужна общая картина, региональным администраторам — изолированный доступ только к своему периметру.

**Архитектурный шаблон:**
- Один кластер в центральном ЦОД; минимум 3 узла для HA.
- Отдельные environments под каждое региональное подразделение + отдельный environment `Central` под системы головной службы.
- Роли настроены так, что региональный администратор видит только свой environment; центральная служба видит все.
- Отдельный Self-monitoring environment для команды, эксплуатирующей сам Dynatrace.

**Технические решения:**
- Environment ActiveGate в каждом регионе (пара основной + резервный для отказоустойчивости).
- Лицензия HU делится между environments по профилю нагрузки; конкретные квоты считаются по фактическому ландшафту заказчика.
- Резервные копии на сетевое хранилище в центральном ЦОД.

**Что даёт такая архитектура:**
- Региональные команды работают независимо, не мешая друг другу.
- Центральная служба имеет сквозную картину всех регионов.
- Нет единой точки отказа самого Dynatrace — отказоустойчивость обеспечивается кластером.
