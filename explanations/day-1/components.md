**Термины темы.**

- **OneAgent / агент**: сборщик данных на хосте.
- **ActiveGate / AG / шлюз**: промежуточный узел между OneAgent и кластером. Агрегирует трафик, запускает Synthetic и Extensions.
- **Cluster Management Console / CMC**: отдельный UI на порту 8021 для администрирования самого кластера.
- **Host Unit / HU**: единица лицензирования хоста.
- **Host group / хост-группа**: логическое объединение хостов для единых политик (обновления, режим мониторинга).
- **Update window / окно обслуживания**: временной слот, когда разрешены обновления агентов.
- **Token / токен**: ключ для регистрации нового ActiveGate в кластере.

**Водораздел: где что настраивается.**

| Где | Что именно |
|---|---|
| **Environment UI** (это 5 страниц ниже) | Поведение агентов и шлюзов: обновления, режим, токены |
| **CMC** | Поведение кластера: лицензии, узлы, обновления ПО самого Dynatrace, бэкапы |
| **На хосте (конфиг агента)** | Первичная регистрация: токен, адрес сервера, имя хост-группы |

## 🎬 Работа с компонентами на пяти экранах

### Шаг 1: OneAgent default mode / режим новых агентов

![OneAgent default mode: выбор режима мониторинга по умолчанию](screenshots/day-1/components/settings/builtindeployment.oneagent.default-mode/OneAgent-default-mode-Environment-Settings-Demo-live-Demo-Live-Dynatrace.png)

Путь: **Settings → Preferences → OneAgent default mode** → `https://guu84124.live.dynatrace.com/ui/settings/builtin:deployment.oneagent.default-mode`.

*Что делает.* Задаёт режим по умолчанию для новых OneAgent, устанавливаемых из раздела Deploy Dynatrace.

*Важно.* Если при установке передать ключ командной строки (`--set-monitoring-mode=infra-only`), значение с этой страницы игнорируется: агент стартует в режиме из ключа. Это нужно, чтобы для разных волн установки задавать разный режим без переключения общей политики окружения.

Иконка замка рядом с заголовком: настройка уровня окружения, менять её может только пользователь с write-правом или Settings API. Это защита от случайного переключения поведения сотен агентов.

**Два режима.**

| Режим | Что собирает | Лицензия |
|---|---|---|
| **Full Stack** | Метрики ОС + трейсы приложений (PurePath) + логи + RUM | Полный тариф HU: лестница 16/32/48 GiB → 1/2/3 HU по [Host Units](https://docs.dynatrace.com/managed/shortlink/host-unit) |
| **Infrastructure** | Только метрики ОС и процессов | 0.3 HU @ 16 GiB RAM (с cap 1.0 при Cloud Infrastructure license): ощутимо дешевле Full-Stack |

*Когда какой режим.*
- **Full Stack**: серверы с боевыми приложениями (Java, .NET, Node.js, PHP). Без этого Dynatrace теряет главное назначение: не видно кода.
- **Infrastructure**: хосты, где только БД без инструментируемого кода, файловые серверы, физические сетевые устройства. Трейсы собрать физически нельзя, метрики ОС идут полным объёмом. Экономия лицензии существенная: сверяться нужно с условиями своего контракта и актуальной таблицей Host Units в документации Dynatrace.

*Глобальное значение vs override.* Эта настройка применяется только к новым установкам. Режим конкретного хоста меняется независимо: через **Host settings → Monitoring mode** или параметр командной строки при установке. Типичная практика в банке: глобально Full Stack, отдельные хосты (прокси, балансировщики, БД без пользовательских приложений) переводятся в Infrastructure вручную.

На этом демо-тенанте текущее значение: **Full Stack**. Жёлтая плашка «Your user does not have the necessary write permissions»: демо-аккаунт только на чтение. На боевом окружении у администратора: активный выпадающий список.

### Шаг 2: OneAgent updates / целевая версия и статус парка

![OneAgent updates: целевая версия и статус парка по семействам ОС](screenshots/day-1/components/settings/builtindeployment.oneagent.updates/OneAgent-updates-Environment-Settings-Demo-live-Demo-Live-Dynatrace.png)

Путь: **Settings → Updates → OneAgent updates** → `https://guu84124.live.dynatrace.com/ui/settings/builtin:deployment.oneagent.updates`.

**Важно сразу.** Эта страница **не включает и не выключает автообновление агентов**. Здесь задают:
1. **Целевую версию**: до какой версии все агенты должны быть подтянуты.
2. **Статус распространения**: сколько уже подтянулось, сколько отстаёт.

Переключатель режима обновления отдельной хост-группы лежит не здесь, а в **Settings → Host groups**.

**Блок Target version / целевая версия.**

Три варианта выбора:
- **Latest stable revision**: последняя стабильная сборка.
- **Previous stable revision**: предпоследняя стабильная.
- **Older stable revision**: ещё более старая.

*Зачем выбирать не последнюю.* Когда Dynatrace выпускает новую стабильную сборку, её сначала применяют клиенты, готовые принять потенциальные регрессии. Через несколько недель она становится «предыдущей стабильной» и уже проверена. Выбирая Previous, парк сдвигается на одну сборку назад: чтобы не быть первыми, кто столкнётся с незамеченной проблемой.

*Типичный выбор в банке.* Previous stable для production: компромисс между свежестью и надёжностью.

**Блок Automatic updates status / статус распространения.**

По подсекциям в разрезе ОС: на снимке темы это Linux x86/64, Linux ARM, Windows, AIX (набор ОС в блоке зависит от вашего парка агентов, у вас он может отличаться: подсекция появляется для той ОС, чьи агенты есть в окружении). В каждой строки вида `X OneAgent instances is outdated. Target revision is 1.AAA.BBB (currently 1.CCC.DDD)`. Читается так: на этой ОС N агентов устарели, целевая сборка 1.AAA.BBB, у них сейчас 1.CCC.DDD. Клик по строке: проваливается в список конкретных хостов с этой версией.

**Air-gapped: как на самом деле работают обновления.**

В закрытом контуре у Dynatrace нет доступа в интернет, новая версия агента не появляется в кластере автоматически. Процесс обновления всегда ручной, два этапа:

1. **Внесение пакета в кластер.** Администратор скачивает дистрибутив OneAgent новой версии с customer portal Dynatrace на отдельной машине с интернетом, переносит в закрытый сегмент (через data-diode, ручной носитель или jump-хост), загружает в кластер через CMC.

2. **Распространение по агентам.** После загрузки пакета новая версия становится доступной в поле Target version. Хост-группы с разрешённым обновлением начинают применять новую сборку в назначенные окна обслуживания.

То есть в закрытом контуре нет автообновлений в привычном смысле. Есть плановые обновления раз в несколько недель или месяцев, которые начинаются с работы администратора по переносу пакетов.

**Как использовать страницу для ревью парка.**

- Отстающих единицы: норма, часть просто не попала в своё окно.
- Отстающих много: одно из трёх:
  - В хост-группах режим обновления = Disabled.
  - Пакет новой версии ещё не загружен в кластер.
  - Окно обслуживания задано слишком узко, агенты не успевают.

**Управление режимом обновления отдельных хост-групп.**

Путь: **Settings → Host groups** → `https://guu84124.live.dynatrace.com/ui/settings/host-groups`. В карточке хост-группы параметр **Update mode**:
- **Disabled**: обновление запрещено.
- **During update window**: только в привязанное окно.
- **As soon as available**: применить, как только новая версия доступна в кластере.

*Типичная схема банка.* Production-группы = During update window с окном в ночь выходных. Dev / test = As soon as available. Критичный legacy = Disabled.

### Шаг 3: Update windows / окна обслуживания

![Update windows: список окон обслуживания агентов](screenshots/day-1/components/settings/builtindeployment.management.update-windows/Update-windows-for-OneAgent-updates-Environment-Settings-Demo-live-Demo-Live-Dyn.png)

Путь: **Settings → Updates → Update windows for OneAgent updates** → `https://guu84124.live.dynatrace.com/ui/settings/builtin:deployment.management.update-windows`.

*Что делает.* Хранит **именованные окна обслуживания**: правила «когда разрешено обновление» в виде набора параметров: время начала, время окончания, дни недели, часовой пояс. Окно создаётся один раз и привязывается к произвольному числу объектов: к агенту, к хост-группе или ко всему окружению.

*Логика разделения.* Правила расписания живут здесь, привязка «какое расписание: какой группе»: в карточке хост-группы через параметр Update window.

**На этом демо-тенанте.** В центре экрана `No data to display`: окон не создано. Это нормальное исходное состояние свежего кластера. После создания первого окна на этом месте появится таблица с колонками: имя, время начала, время окончания, дни недели, часовой пояс, список привязанных объектов.

**Создание окна на боевой инсталляции.** Кнопка **+ Add window** в правом верхнем углу (на скрине скрыта, demo = read-only). Форма:

- **Name**: понятное имя, например `prod-weekend-night` или `dev-daily-night`. Используется для привязки из хост-групп: схема именования должна быть однозначной.
- **Start time** / **End time**: время в формате `HH:MM`.
- **Days of week**: чекбоксы дней недели.
- **Timezone**: часовой пояс. Для Казахстана: `Asia/Almaty`.

**Типичные значения.**

| Группа | Окно |
|---|---|
| Production в банке | Start 02:00, End 05:00, Sat+Sun, Asia/Almaty |
| Dev / test | Окна не нужны: режим As soon as available в хост-группе |
| Критичный legacy | Либо узкое окно раз в месяц под согласованную дату, либо Disabled |

**Почему окно не меньше 3 часов.** Агент начинает скачивание в границах окна, к концу окна должен завершить установку. Если не успел: процесс останавливается в безопасной точке, следующая попытка: в начале следующего окна (через неделю). На хосте ничего не ломается, но версия остаётся между старой и новой.

В хост-группе с десятками хостов короткое окно (1 час) физически не даёт завершить цикл. Рекомендованный минимум: 3 часа, оптимум 4–5.

**Обработка казахстанских праздников.** Окна на этой странице поддерживают только еженедельное расписание. Праздничные даты как таковые не задаются: если в окне отмечена суббота, агент будет обновляться каждую субботу, включая праздничные.

Для обработки праздников используется связка с **Maintenance windows** (**Settings → Preferences → Maintenance windows**). Maintenance window: универсальная настройка «окон тишины» с возможностью задать конкретные даты и исключения. В production-практике на них маркируются Наурыз, День Конституции, День Республики и производственные стоп-дни конкретного банка.

**Важно.** Update window (эта страница) и Maintenance window (отдельная страница): **разные сущности**, не пересекаются автоматически. Администратор поддерживает два списка. На периоды праздников Update window отключается вручную или хост-группы временно переводятся в Disabled.

### Шаг 4: ActiveGate updates / автообновления шлюзов

![ActiveGate updates: общий тумблер автоматических обновлений](screenshots/day-1/components/settings/builtindeployment.activegate.updates/ActiveGate-updates-Environment-Settings-Demo-live-Demo-Live-Dynatrace.png)

Путь: **Settings → Updates → ActiveGate updates** → `https://guu84124.live.dynatrace.com/ui/settings/builtin:deployment.activegate.updates`.

**Что на экране.** Минимум элементов: заголовок, короткое описание, ссылка на release notes и один тумблер. Таблицы статуса по ОС нет: шлюзов в инсталляции единицы, не сотни. Их состояние смотрят в **Settings → Monitoring → ActiveGates**.

Под заголовком: ссылка **ActiveGate release notes** на сайт Dynatrace. Используется на практике: перед разрешением автообновления администратор читает список изменений и проверяет, нет ли breaking changes и конфликтов с установленными Extensions. В банке это обязательный шаг change-management.

**Единственный контрол: тумблер Automatic updates at earliest convenience.**

*Выключен.* Шлюзы остаются на текущей версии, обновление возможно только вручную запуском установщика на хосте.

*Включён.* Все Environment ActiveGate окружения начинают переходить на новую версию, как только она доступна в кластере и нагрузка позволяет безопасно перезапустить dtgateway.

**Ключевой риск автообновления.** В рабочей инсталляции обычно 2–4 Environment ActiveGate для распределения нагрузки и резервирования. При одновременном обновлении всех шлюзов OneAgent на всех хостах теряют связь с кластером на время перезапусков `dtgateway`: обычно несколько минут (точная длительность зависит от размера ActiveGate, числа активных модулей и нагрузки; в публичной документации Dynatrace фиксированного SLA на длительность нет). На время перерыва OneAgent буферизует события локально и отправляет их при восстановлении связи: конкретное окно буфера в публичных документах одной цифрой не зафиксировано, на практике хватает на типичный перезапуск AG. Но:

- Графики всех сервисов одновременно покажут пропуск.
- Если в этот момент в приложении случится инцидент, Davis AI его не обнаружит из-за отсутствия данных для анализа.

**Типичная практика для банка.** Тумблер выключен. Администратор обновляет шлюзы по графику, с разносом по времени:
- Шлюз 1 во вторник ночью.
- Шлюз 2 в четверг ночью.
- Шлюз 3 через неделю.

График гарантирует, что одновременного перезапуска всех шлюзов не произойдёт.

**Альтернативный подход.** Тумблер включён глобально, на части шлюзов отключается на уровне конфигурации хоста: `/var/lib/dynatrace/gateway/config/custom.properties`, параметр `update.enabled=false`. Эти шлюзы игнорируют глобальную настройку и обновляются только вручную. Разделение на «экспериментальные» (обновляются автоматически сразу) и «консервативные» (обновляются отдельно после подтверждения).

**Air-gapped.** Тот же механизм: новая версия ActiveGate появляется в кластере только после ручной загрузки администратором через CMC. До этого тумблер включён или выключен: не важно, обновляться не во что.

### Шаг 5: Network security / политика токенов ActiveGate

![Network security: политика аутентификации и уведомления о токенах](screenshots/day-1/components/settings/builtinactivegate-token/Network-security-Environment-Settings-Demo-live-Demo-Live-Dynatrace.png)

Путь: **Settings → Preferences → Network security** → `https://guu84124.live.dynatrace.com/ui/settings/builtin:activegate-token`.

**Важно.** На этой странице **не создаются и не отзываются сами токены**. Здесь: только политика работы с токенами на уровне окружения. Выпуск и отзыв: **Settings → Access tokens** (`https://guu84124.live.dynatrace.com/ui/access-tokens`): там кнопка **+ Generate new token**, выбор scope, срока действия, таблица выпущенных токенов с Revoke. Структура токена: три части `<prefix>.<24-символьный public>.<64-символьный secret>`; разные префиксы соответствуют разным типам токенов: `dt0s01`: API tokens, `dt0s02`/`dt0s03`/`dt0s08`: OAuth2 clients, `dt0s06`: OAuth2 refresh tokens, `dt0s16`: Platform tokens. <!-- last-verified: 2026-04-27 source: docs.dynatrace.com/managed/manage/access-control/access-tokens -->

**На что отвечает эта страница.**
1. Обязательно ли требовать валидный токен для подключения нового ActiveGate к кластеру.
2. Включены ли уведомления о предстоящем истечении токенов.

**Mutual TLS.** Описание под заголовком: о двухстороннем контроле безопасности. При подключении нового ActiveGate к кластеру обе стороны обмениваются информацией для взаимной проверки. Конкретный механизм mutual TLS как именованной фичи в публичной документации `/managed/` отдельной страницей не зафиксирован: поведение страницы Network security описано на самой странице окружения. Логика проверки:
- Кластер проверяет валидность токена шлюза.
- Шлюз проверяет валидность TLS-сертификата кластера.

Соединение устанавливается только после успешной проверки обеих сторон. Стандартная реализация mutual TLS с аутентификацией по токену.

**Зелёная плашка.** `ActiveGate tokens are enforced automatically in your environment`. В свежих инсталляциях политика принудительного использования токенов включается по умолчанию: только шлюзы с валидным токеном могут подключиться.

**Радио-опция Manually enforce ActiveGate token authentication.** Для окружений, мигрированных со старых версий, где принудительная политика не включалась по умолчанию. В новых окружениях с зелёной плашкой эта опция не требуется.

**Тумблер Enable notifications about ActiveGate tokens expiration dates.**

*Что делает.* Включает уведомления о токенах, которые скоро истекут или уже истекли. Уведомления отправляются в настроенные каналы (**Settings → Integration → Problem notifications**).

*Когда включать.* Рекомендуется всегда. Администратор за несколько дней получает предупреждение и успевает выпустить новый токен до того, как в процедуре регистрации нового шлюза возникнет ошибка.

*ЕСЛИ→ТО.* Включишь тумблер: за несколько дней до истечения токена уведомление уйдёт в настроенные каналы Problem notifications, и токен успеют заменить заранее. Выключишь: токен истечёт молча, и это всплывёт только в момент, когда регистрация нового ActiveGate вернёт ошибку «недействительный токен».

**Нюанс про истечение токена.** Истечение **не влияет на уже зарегистрированные шлюзы**. Токен используется только в момент регистрации: шлюз предъявляет токен, кластер в ответ выдаёт постоянный сервисный ключ. Дальше все соединения идут по этому ключу, токен не участвует. Истечение блокирует только регистрацию новых шлюзов с этим токеном.

*Типичная практика.* Токены выпускают с ограниченным сроком (например, 90 дней) под конкретную волну развёртывания шлюзов и спокойно дают им истечь, когда волна завершилась.

## 🎓 ТЕОРИЯ: обновления в air-gapped и ревью здоровья парка

### Как обновляется кластер в air-gapped

В облачной версии Dynatrace (SaaS) обновления прилетают сами. В air-gapped Managed: всё вручную через пять шагов.

**Шаг 1. Администратор на машине с интернетом.** Скачивает с customer portal Dynatrace:
- **Cluster update package**: обновление серверного ПО (`dynatrace-managed-cluster-update-X.Y.Z.tar.gz`).
- **OneAgent packages**: установщики и обновления агентов для всех используемых ОС.
- **ActiveGate packages**: аналогично для шлюзов.
- Релиз-ноты и SHA256-контрольные суммы для проверки целостности.

**Шаг 2. Перенос через шлюз обмена (air-gap gateway).** У банка есть специальный DMZ-шлюз между сегментом с интернетом и изолированным. Варианты:
- **Однонаправленный data-diode**: самый жёсткий вариант, только из внешней в изолированную.
- **Ручной перенос на USB или оптическом диске**: классика.
- **SCP через jump-хост** с контролем содержимого.

**Шаг 3. Загрузка в CMC.**
1. Открыть CMC (`https://<кластер>:8021/cmc`).
2. **Cluster updates → Upload**.
3. Загрузить `.tar.gz` пакет кластера.
4. CMC валидирует SHA256 и показывает, что обновление готово к применению.

**Шаг 4. Применение обновления кластера.**
1. В CMC: кнопка **Apply update**.
2. CMC последовательно обновляет узлы кластера (по одному, чтобы сервис оставался доступен).
3. На каждом узле короткий rolling restart компонентов (Server, Cassandra, Elasticsearch). UI может «мигнуть» на 10–30 секунд, данные не теряются: они буферизуются в ActiveGate.

**Шаг 5. Обновление агентов и шлюзов.** После обновления кластера пакеты OneAgent и ActiveGate тоже загружаются в кластер через CMC. После этого:
- Если на странице OneAgent updates включён тумблер для семейства ОС: агенты применят новую версию в своё окно обслуживания.
- Если выключен: версия лежит в кластере, ждёт ручного применения.

**Ключевой момент для безопасника.** В изолированном контуре Dynatrace не обращается во внешний мир. Все обновления: через ручной перенос. Кластер сам не пытается сходить в интернет, даже проверка лицензии не требует выхода наружу.

### Чеклист ежемесячного ревью здоровья парка

**OneAgent.**
1. Deployment status → фильтр Offline: сколько агентов потеряли связь.
2. Deployment status → сортировка по Version: сколько агентов отстали больше чем на 2 минорные версии.
3. Для агентов с Failed: открыть детали, посмотреть причину.
4. Новые хосты (за месяц) попали в правильные host groups: иначе настройки для них не сработают.

**ActiveGate.**
1. Settings → Monitoring → ActiveGates: все ли в Active.
2. Нагрузка каждого (CPU / Memory): если выше 70% постоянно, пора добавлять ещё один шлюз.
3. Версии шлюзов совпадают с целевой.

**Лицензии (в CMC).**
1. License → Host Units: сколько использовано, сколько осталось. Меньше 10% свободно: планировать расширение или оптимизировать режим на хостах.
2. License → DEM Units: если используется RUM или Synthetic.

**Кластер (в CMC).**
1. Cluster nodes: все узлы в Running.
2. Cluster state → Cassandra и Elasticsearch в состоянии green.
3. Свободное место на дисках узлов больше 25% (меньше: риск OOM).

### Типичные ситуации и что делать

**Агент установлен, но не появляется в Deployment status.**
- Проверить исходящую связность с хоста до кластера на 443: `curl -vk https://<кластер>/api/v1/deployment`.
- Проверить валидность сертификата кластера с точки зрения хоста. Если корпоративный CA: он должен быть в truststore.
- Логи агента: `/var/log/dynatrace/oneagent/installer/installation.log`.

**Шлюз стоит, но OneAgent не подключаются через него.**
- На хосте с OneAgent: `cat /var/lib/dynatrace/oneagent/agent/runtime/config/deployment.conf`: там должен быть адрес ActiveGate.
- Проверить, что порт 9999 открыт от хоста до шлюза.
- Перезапустить OneAgent: `systemctl restart oneagent`.

**После обновления кластера агенты перестали слать данные.**
- Чаще всего: несовместимость версий. Проверить Support matrix: версия агента N поддерживает кластер версии N, N+1. Если кластер поднялся до N+3: старые агенты отваливаются.
- Решение: разрешить автообновление на странице OneAgent updates → агенты подтянутся до совместимой версии.

**В списке ActiveGates остался ghost-шлюз, который давно не работает.**
- В Environment UI удалить нельзя.
- CMC → ActiveGates → найти по имени или IP → Remove.
- Там же стоит проверить, нет ли зависших записей после предыдущих миграций.
