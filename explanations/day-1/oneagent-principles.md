**Термины темы.**

- **OneAgent / агент** — программа-сборщик данных, устанавливаемая на каждый хост под мониторингом.
- **Feature / возможность / сенсор** — отдельный модуль OneAgent, отвечающий за мониторинг одной технологии (ASP.NET, Java Akka, AWS Lambda, eBPF networking).
- **Opt-In** — статус фичи: по умолчанию выключена, включается администратором вручную.
- **Deep monitoring / глубокий мониторинг** — инструментация кода приложения (построение PurePath, не только метрики ОС).
- **Process Group / группа процессов** — логическое объединение одинаковых процессов в одну сущность для удобного отображения.

**Связь с соседними темами.**

| Настройка | Где настраивается | Как влияет на OneAgent |
|---|---|---|
| Режим мониторинга | **OneAgent default mode** + Host settings | Full Stack = все сенсоры; Infrastructure = инструментация кода отключена |
| Автообновление | **OneAgent updates** + Host group Update mode | Какая сборка OneAgent применяет эти принципы |
| Host group | Назначается при установке | Позволяет применять разные правила и фичи к разным группам хостов |

## 🎬 Работа с принципами OneAgent на трёх экранах

### Шаг 1 — OneAgent features / возможности агента

![OneAgent features — список всех возможностей инструментации с тумблерами](screenshots/day-1/oneagent-principles/settings/builtinoneagent.features/OneAgent-features-Environment-Settings-Demo-live-Demo-Live-Dynatrace.png)

Путь: **Settings → Preferences → OneAgent features** → `https://guu84124.live.dynatrace.com/ui/settings/builtin:oneagent.features`.

**Что на экране.** Весь набор возможностей инструментации OneAgent. Каждая строка — отдельная feature (сенсор или набор правил для мониторинга конкретной технологии). Список длинный, разбит на страницы. Внизу видна пагинация до 18-й страницы.

Под заголовком Dynatrace поясняет политику: по умолчанию включается только базовый набор. Дополнительные фичи с меткой **Opt-In** активирует администратор вручную. Цель — чтобы свежеустановленный агент не создавал избыточной нагрузки и объёма данных на хосте, а дополнительные возможности включались осознанно. Полный перечень режимов (Full Stack / Infrastructure / Application-only) описан в [OneAgent overview](https://docs.dynatrace.com/managed/shortlink/oneagent). <!-- last-verified: 2026-04-27 source: docs.dynatrace.com/managed/shortlink/oneagent -->

Зелёная плашка с инфо-иконкой сверху сообщает, что часть возможностей на этом тенанте уже активирована.

**Таблица возможностей. Колонки:**

- **Enabled** — тумблер включения. Основной контрол для управления фичей.
- **Summary** — короткое описание. Часто с пометкой технологии (ASP.NET, .NET Framework, Java Akka, AWS Lambda, Business Events) и статусом Opt-In.
- **Min. OneAgent version** — минимальная версия OneAgent, в которой фича работает. Если парк агентов на более старой сборке, тумблер виден, но фича не заработает.
- **Details** — раскрывающаяся карточка: описание, ссылка на документацию, параметры настройки.

**Что за фичи живут в списке. Три категории.**

- **Per-технологические сенсоры для кода приложений.** Отдельные строки для каждой версии ASP.NET (MVC, MVC5, Web API 2, Core), для Java-фреймворков (Akka, Spring, Vert.x), для Node.js, Go, Python, PHP, Ruby. Каждая — модуль, знающий как внедриться в конкретную версию среды выполнения и снять оттуда данные.
- **Сенсоры для платформ и сервисов.** AWS Lambda, AWS DynamoDB SDK, AWS SNS, AWS SQS, Azure Functions, Business Events, OpenTelemetry integration.
- **Сенсоры для подсистем.** eBPF для сетевого трейсинга, zero-code vulnerability evaluation, прочие интеграции.

**Когда администратор трогает эту страницу. Три типичные ситуации.**

- **Новая технология в инфраструктуре.** Команда мигрировала сервис на Python FastAPI, просят включить мониторинг. Администратор находит через фильтр позицию с упоминанием Python, проверяет, что минимальная версия поддерживается парком, включает тумблер. OneAgent на хостах, где обновилась настройка, начинает инструментировать Python-процессы — в интерфейсе появляются трейсы.
- **Подозрение на конфликт.** В логах приложения появились ошибки, связанные с инструментацией. Администратор находит подозрительный сенсор в списке, отключает, проверяет — пропала ли проблема. Если да — оставляет выключенным, фиксирует находку во внутреннем журнале изменений и обсуждает с командой приложения план дальнейшей диагностики.
- **Аудит перед годовым ревью.** Проход по списку, отключение всего, что не используется в контуре — снижение нагрузки агента на хосты.

**Ограничение в air-gapped.** Возможности привязаны к версии OneAgent. Чтобы иметь все свежие фичи, парк агентов должен быть на актуальной сборке. В закрытом контуре сборки появляются только после ручной загрузки через CMC. Фича из последнего релиза доступна только после того, как администратор перенёс пакет OneAgent с интернет-машины, загрузил в кластер и дал парку обновиться в ближайшее окно обслуживания. До этого момента тумблер фичи виден, но не работает для агентов старой версии. В колонке Min. OneAgent version тогда стоит номер выше текущего парка.

**Работа с отдельной фичей.** Клик по стрелке в колонке Details раскрывает карточку с расширенным описанием: какие процессы на хосте будут инструментироваться, какие данные начнут собираться, какие параметры у сенсора, ссылка на документацию. В некоторых карточках есть дополнительные переключатели — например, для Business Events можно отдельно включить сбор событий по HTTP-запросам и по логам.

**Связь с Host settings.** Тумблеры на этой странице действуют на уровне всего окружения. Включение = фича активна для всех хостов с достаточно новым OneAgent. Для точечного отключения на конкретном хосте используется **Host settings → OneAgent features** — переопределение глобальных решений для отдельной машины. На практике нужно редко, обычно для серверов, где определённая инструментация конфликтует с приложением.

### Шаг 2 — Process group monitoring / главный переключатель

![Process group monitoring — главный переключатель глубокого мониторинга](screenshots/day-1/oneagent-principles/settings/builtinprocess.process-monitoring/Process-group-monitoring-Environment-Settings-Demo-live-Demo-Live-Dynatrace.png)

Путь: **Settings → Processes and containers → Process group monitoring** → `https://guu84124.live.dynatrace.com/ui/settings/builtin:process.process-monitoring`.

**Что на экране.** Страница с главным переключателем глубокого мониторинга процессов. Слева раскрыт раздел **Processes and containers** с несколькими подпунктами — они формируют механику распознавания и инструментации.

Под заголовком Dynatrace поясняет: OneAgent автоматически распознаёт группы процессов на хосте и решает, какие из них нуждаются в глубоком мониторинге. Для полноценной инструментации серверы приложений (особенно Java и .NET) нужно перезапустить после установки агента — чтобы инструментация встроилась с самого старта процесса. Обычно это делается при ближайшем плановом рестарте, отдельный downtime специально для агента не требуется.

**Главный контрол — тумблер Enable automatic deep monitoring.**

*Что делает.* Когда включён, OneAgent на всех хостах (где не переопределено вручную) применяет полный цикл: обнаруживает процессы, сопоставляет с правилами, определяет группу, запускает инструментацию для серверов приложений.

*Когда выключен.* OneAgent перестаёт автоматически включать глубокий мониторинг на новых процессах. Метрики ОС и процессов по-прежнему собираются, но PurePath не строятся, код не инструментируется.

*Когда это нужно.* Редко. Основной сценарий — период стабилизации приложения перед масштабным изменением, когда команда хочет исключить инструментацию как возможную причину проблем.

**Подпункты раздела Processes and containers.**

- **Process instance snapshots** — моментальные снимки процессов для подробной диагностики.
- **Process availability** — правила отслеживания доступности процессов (когда считать, что процесс упал).
- **Process group detection** — правила, как отдельные процессы объединяются в группы (сто копий одного сервиса должны восприниматься как одна сущность).
- **Process group monitoring** — текущая страница с главным переключателем.
- **Built-in detection rules** — предустановленные правила распознавания для популярных технологий (следующий Шаг).
- **Simple / Advanced detection rules** — упрощённый и полноценный интерфейсы для кастомных правил.
- **Declarative process grouping** — декларативное описание групп.
- **Process grouping rules** — правила объединения процессов для отображения.

**Как работает механика в целом.** OneAgent на хосте запускает свой процесс мониторинга. Тот сканирует список всех процессов ОС, читает информацию из `/proc` на Linux или из соответствующих API на Windows, применяет правила распознавания. Для процессов, определённых как серверы приложений, OneAgent запускает модуль инструментации:
- **Java** — через параметр `-javaagent`.
- **.NET** — через CLR Profiling API.
- **Node.js** — через подмену require-модулей.
- **Go** — поддерживается автоматическая инструментация 64-битных бинарей на x86 и ARM64; конкретный механизм встраивания — внутреннее устройство OneAgent (детали и поддерживаемые версии — в разделе Technology support документации Dynatrace для вашей версии).
- **Ruby** — отдельного нативного агента под Ruby нет; телеметрия снимается через OpenTelemetry SDK и отправляется в Dynatrace по OTLP.

После успешной инструментации процесс начинает отправлять данные о каждом обработанном HTTP-запросе, каждом вызове базы, каждом исключении в коде. Совместимость конкретной технологии с конкретной версией OneAgent проверяется в матрице Technology support в документации Dynatrace.

**Типичные сценарии работы с этой страницей.**

- **Выключить deep monitoring для несовместимой хост-группы.** Старое Java-приложение ломается при внедрении сторонних агентов. Администратор идёт в **Host settings → Processes and containers → Process group monitoring** для этой группы, переопределяет глобальное значение на Disabled. На остальных группах глобальный тумблер включён и продолжает работать.
- **Корректировка правил распознавания.** Агент распознал процесс как generic, без специфических метрик. Нужно добавить кастомное правило. Переходим на Built-in process monitoring rules — Шаг 3.

### Шаг 3 — Built-in process monitoring rules / встроенные правила

![Built-in process monitoring rules — список предустановленных правил распознавания](screenshots/day-1/oneagent-principles/settings/builtinprocess.built-in-process-monitoring-rule/Built-in-process-monitoring-rules-Environment-Settings-Demo-live-Demo-Live-Dynat.png)

Путь: **Settings → Processes and containers → Process group monitoring → Built-in process monitoring rules** → `https://guu84124.live.dynatrace.com/ui/settings/builtin:process.built-in-process-monitoring-rule`.

**Что на экране.** Каталог предустановленных правил распознавания процессов. Каждая строка — одно правило: по каким признакам (имя бинаря, параметры запуска, файлы конфигурации, переменные окружения) OneAgent относит процесс к определённому типу и включает соответствующую инструментацию.

**Что покрывают правила.** Типичные технологии в инфраструктуре:

- **Серверы приложений** — Apache Tomcat, JBoss, WildFly, WebSphere, WebLogic.
- **Веб-серверы** — Apache httpd, Nginx, Microsoft IIS.
- **Базы данных** — Oracle, PostgreSQL, MySQL, Microsoft SQL Server, MongoDB.
- **Очереди сообщений** — RabbitMQ, ActiveMQ, Kafka.
- **Платформенные процессы** — Kubernetes kubelet, Docker daemon, containerd.
- **Языковые рантаймы** — Java JVM, .NET Core, Node.js, Python, PHP-FPM, Ruby.

Для каждой технологии есть правило «как её узнать» и «к какому типу процесса отнести». Матрица доступности возможностей по платформам приведена в OneAgent platform and capability support matrix в документации Dynatrace для вашей версии.

**Почему нельзя просто включить всё и забыть.** На крупной инсталляции одно имя процесса используется разными приложениями в разных командах. Пример: процесс `java` с одним bootstrap-классом может быть и собственным сервисом, и сторонним вендорским продуктом. Без правильных правил оба попадут в одну группу, метрики смешаются, разобрать проблему сложно. Правила на этой странице решают: каждое задаёт набор условий, по которым процесс идентифицируется однозначно.

**Структура правила.**

- **Технология** — к чему правило относится (Java, .NET, Kafka, Nginx).
- **Условия** — логический набор проверок для применения правила (командная строка содержит строку, процесс слушает порт, переменная окружения имеет значение).
- **Действие** — что OneAgent делает с процессом: как его назвать, в какую группу поместить, какие метрики снимать.

**Редактирование встроенных правил.** Нельзя. Администратор может только включать и выключать. Для изменения поведения — **Custom process monitoring** (`https://guu84124.live.dynatrace.com/ui/settings/builtin:process.custom-process-monitoring`). Там собственные правила с теми же возможностями, но с приоритетом выше встроенных.

**Типичные сценарии работы.**

- **После установки OneAgent на новый сервер.** Приложение распознано неправильно — собственный сервис отображается как generic-Java без специфических метрик. Администратор либо находит подходящее встроенное правило и включает его, либо пишет кастомное.
- **Внедрение новой платформы.** Kafka впервые появилась в контуре — администратор проверяет, что правило для Kafka в списке включено, и убеждается, что процессы Kafka корректно распознаются.
- **Расследование инцидента со странными группировками.** Инженер сверяется со списком правил, чтобы понять, как агент решил сгруппировать эти процессы.

**Связь с air-gapped.** Встроенные правила поставляются со сборкой OneAgent и кластера. Когда Dynatrace выпускает поддержку новой технологии (новая версия Kubernetes с новым способом идентификации кластерного процесса), правило появляется в свежей сборке. В закрытом контуре до тех пор, пока администратор не загрузит новую сборку через CMC, правила не будет — процессы новой технологии будут распознаваться по старым правилам или как generic.

**Связь со Smartscape.** После того как процессы распознаны и сгруппированы по правилам с этой страницы, они становятся видимыми сущностями на карте Smartscape и в списках: Services, Databases, Queues. Без правильного распознавания приложение не получит своего места в топологии, трейсы запросов будут показывать безымянные generic-узлы.
