**Термины темы.**

- **Dashboard / дашборд / панель мониторинга**: страница с набором виджетов.
- **Widget / виджет / плитка**: один элемент на странице: график, число, таблица, карта.
- **Preset / пресет / встроенный дашборд**: готовая панель из коробки Dynatrace, править нельзя, только клонировать.
- **Custom dashboard / пользовательский дашборд**: панель, которую инженер собрал сам.

## 🎬 Работа с дашбордами на четырёх экранах

### Шаг 1: Dashboards / список панелей

![Dashboards: список дашбордов с фильтрами](screenshots/day-1/dashboards/dashboards/Dashboards-Demo-live-Demo-Live-Dynatrace.png)

Путь: **Observe and explore → Dashboards** → `https://guu84124.live.dynatrace.com/ui/dashboards`.

**Что на экране.** Список всех дашбордов окружения. На этом демо-тенанте их 618: пресеты плюс пользовательские, накопленные за время жизни окружения. На боевой инсталляции количество зависит от того, сколько дашбордов завели инженеры: оно не характеристика платформы, а показатель использования.

**Две кнопки в правом верхнем углу.**

- **Import dashboard**: загрузить готовый дашборд из JSON-файла. Так переносят панели между окружениями (например, с тестового на прод) или восстанавливают из бэкапа.
- **Create dashboard**: создать пустой дашборд и редактировать с нуля.

**Слева: панель фильтров.** Сужают список.

- **Ownership / владение**: свои, расшаренные мне, все.
- **Favorite / избранное**: отмеченные звёздочкой.
- **Owner / автор**: выбор по конкретному пользователю. На этом демо в списке свыше 260 имён; на боевом будет столько, сколько у банка инженеров с правом создавать панели.
- **Tag / тег**: по тегу, который автор присваивает для группировки. На демо свыше 500 тегов.
- **Preset / пресет**: показать только встроенные или только пользовательские.

**Таблица.** Колонки: звёздочка-избранное, имя, Popularity (полоска частоты использования: видно, что реально смотрят, а что: забытое наследие), дата последнего изменения, автор. У встроенных рядом с именем стоит метка **Preset**.

**Открытие дашборда.** Клик по имени открывает панель в режиме просмотра. Виджеты подтягивают данные за выбранный период (верхний селектор времени, по умолчанию Last 2 hours). Фильтр Management zones в шапке влияет на все виджеты разом.

**Редактирование.**

- У своих дашбордов: кнопка **Edit** в правом верхнем углу: добавлять виджеты из палитры, двигать, менять запросы.
- Пресеты править нельзя. Кнопка **Clone** создаёт копию в своих: её уже можно редактировать.
- Удобный приём для сбора виджета: настроить нужный график в Data Explorer и нажать **Pin to dashboard**: виджет переедет на выбранную панель.

**Дашборд как код.** Дашборд внутри, это JSON со списком виджетов, их запросами и позициями.

- Через **Import dashboard**: залить JSON из внутреннего репозитория шаблонов.
- Через API `GET /api/config/v1/dashboards/{id}`: выгрузить текущий дашборд наружу и положить в Git.

Зачем это нужно. В банке изменения в production идут через ревью: так работает change-management. Если дашборды хранятся в Git, каждое изменение видно в diff, ревьюится через pull request и накатывается скриптом при деплое. Руками в UI: только на dev и test.

### Шаг 2: General settings / общие настройки

![General settings: анонимный доступ и дашборд-домашняя страница](screenshots/day-1/dashboards/settings/builtindashboards.general/General-settings-Environment-Settings-Demo-live-Demo-Live-Dynatrace.png)

Путь: **Settings → Dashboards → General settings** → `https://guu84124.live.dynatrace.com/ui/settings/builtin:dashboards.general`.

На экране два блока.

---

**Блок 1: Allow anonymous access / анонимный доступ к дашбордам.**

*Что делает.* Когда тумблер включён, автор конкретного дашборда может в его настройках включить «поделиться по ссылке без логина». Любой, у кого есть ссылка, откроет такой дашборд без авторизации.

*Зачем нужно.* Показать дашборд на большом мониторе в диспетчерской: без логинов каждый час. Встроить на внутренний портал: тоже удобнее без логина. Информационный экран в офисе.

*Риск.* Через ссылку без авторизации видны имена сервисов, метрики отклика, иногда: имена клиентов в URL. Если ссылка утечёт наружу, эти данные утекут вместе с ней.

*Как обычно делают в банке.* Тумблер включают, но публикуют анонимно не всё подряд, а только специально собранные дашборды, где нет чувствительных имён и конкретных данных клиентов.

*ЕСЛИ→ТО.* Включишь тумблер: автор сможет открыть конкретный дашборд по ссылке без логина, и любой с этой ссылкой увидит имена сервисов и метрики. Оставишь выключенным: поделиться публичной ссылкой нельзя, дашборд откроется только после авторизации.

---

**Блок 2: Home dashboards / стартовая страница для группы пользователей.**

*Что делает.* Задаёт правило «для LDAP-группы X при входе в Dynatrace показывать дашборд Y как стартовую страницу».

*Зачем нужно.* Инженер при входе должен попадать сразу на свой рабочий дашборд, а не на пустой экран или общий обзор.

*Как обычно делают в банке.* Для каждой команды своё правило: DevOps: дашборд инфраструктуры, DBA: дашборд баз, фронтендеры: дашборд RUM. На этом демо-тенанте правил нет, в центре блока `No data to display`. На боевой инсталляции добавляются кнопкой **+ Add mapping**: выбрать группу → выбрать дашборд → сохранить.

### Шаг 3: Preset settings / управление пресетами

![Preset settings: видимость пресетов в окружении](screenshots/day-1/dashboards/settings/builtindashboards.presets/Preset-settings-Environment-Settings-Demo-live-Demo-Live-Dynatrace.png)

Путь: **Settings → Dashboards → Preset settings** → `https://guu84124.live.dynatrace.com/ui/settings/builtin:dashboards.presets`.

---

**Блок 1: Enable presets / включение пресетов.**

*Что делает.* Тумблер. По умолчанию пресеты видны всем пользователям окружения. Когда выключен: пресеты пропадают из списка дашбордов у всех, кроме разрешённых групп.

*Зачем выключать.* Пресетов в свежей установке Dynatrace: сотни. Если команда реально пользуется пятью, остальные только засоряют навигацию. Чистое окружение: без пресетов по умолчанию, включаются точечно для конкретных команд.

---

**Блок 2: Limit preset visibility / ограничение видимости пресета.**

*Что делает.* Правила «пресет X виден только группе Y». Другие пользователи его не увидят в списке дашбордов.

*Зачем нужно.* Сегментация по ролям. DevOps-инженеру пресеты по базам данных не нужны: они только отвлекают. DBA не нужны пресеты RUM. Каждой команде: свой набор релевантных пресетов.

На этом демо-тенанте правил нет: все пресеты видны всем. На боевой инсталляции добавляются кнопкой **+ Add mapping**: выбрать пресет → выбрать группу → сохранить.

### Шаг 4: Allowed URL pattern rules / разрешённые URL картинок

![Allowed URL pattern rules: белый список доменов для картинок в виджетах](screenshots/day-1/dashboards/settings/builtindashboards.image.allowlist/Allowed-URL-pattern-rules-Environment-Settings-Demo-live-Demo-Live-Dynatrace.png)

Путь: **Settings → Dashboards → Allowed URL pattern rules** → `https://guu84124.live.dynatrace.com/ui/settings/builtin:dashboards.image.allowlist`. Рядом с заголовком плашка **Early adopter**: функция молодая, в разных сборках Managed может отличаться по набору опций.

*Что делает.* Белый список доменов, с которых в виджеты дашборда (**Markdown**, **Image**) разрешено подтягивать картинки. Если картинка со внешнего URL не попадает ни под одно правило: Dynatrace её не загружает.

*Зачем нужно.* В виджет Markdown можно написать ссылку на внешнюю картинку: `![logo](https://external.example.com/logo.png)`. Без белого списка Dynatrace тянет картинки с любого URL.

*Какой риск.* Злоумышленник с правом редактировать дашборд вставляет в Markdown ссылку на свой сервер. При каждом просмотре дашборда у любого пользователя к этому серверу уходит HTTP-запрос. Что утекает:
- Факт просмотра дашборда (кто, когда, с какого IP).
- Через цепочку редиректов: cookies пользователя.
- Потенциально: другие заголовки сессии.

*Как решают.* Белый список. Разрешают только те домены, которым доверяют: внутренняя корпоративная вики (Confluence), файловое хранилище, внутренний CDN банка. Внешние интернет-домены не попадают в список: в air-gapped контуре они всё равно недоступны, а полагаться на внешние ресурсы для внутренних дашбордов нет причин.

*На экране.* Таблица **List of URL pattern matchers**. На этом демо одно правило: `Starts with 'https://www.dropbox.com/s/eyp7x72fyohmqyq/'`: остаток от какого-то демо-сценария, в боевом окружении это уберут.

*Добавление правила.* Кнопка **+ Add rule** (в read-only режиме скрыта). По [Global Dynatrace dashboard settings](https://docs.dynatrace.com/managed/analyze-explore-automate/dashboards-classic/dashboards/dashboards-settings) поддерживаются ровно **два типа правил**:
- **Starts with / начинается с**: URL должен начинаться со строки-шаблона.
- **Exact (Equals) / точное совпадение**: URL равен шаблону целиком.

Опции «Regular expression» в публичной документации Dynatrace для классических Dashboard image URL pattern rules **нет**. <!-- last-verified: 2026-04-27 source: docs.dynatrace.com/managed/analyze-explore-automate/dashboards-classic/dashboards/dashboards-settings -->

*ЕСЛИ→ТО.* Добавишь домен в белый список: картинки с него в виджетах Markdown и Image будут подгружаться. Не добавишь: Dynatrace не загрузит картинку с этого URL, и встроенный в Markdown внешний запрос с неё не уйдёт.

## 🎓 ТЕОРИЯ: как проектируют дашборды в банке

### Три слоя дашбордов

В Dashboards Classic: основном формате для Managed: принято делить панели на три слоя по аудитории.

**Оперативные.** Один-два дашборда для дежурной смены. На них ключевые метрики инфраструктуры, статус критичных сервисов (Response time / время отклика, Failure rate / процент ошибок, Throughput / нагрузка), активные проблемы, состояние Synthetic. Висят на больших мониторах в диспетчерской, автообновление раз в минуту. В норме всё зелёное: любая красная полоса сразу ловит глаз.

**Бизнесовые.** Для руководства. Доступность ключевых систем за день и за месяц, конверсия (сколько пользователей успешно провели ключевую операцию), объёмы транзакций, SLA-индикаторы. Технических деталей минимум: цвет индикаторов и динамика во времени.

**Инженерные.** По одному на команду разработки. Детализация по своим сервисам: ключевые метрики, топ ошибок, топ-10 медленных запросов, потребление ресурсов, события деплоев. Плотно набиты виджетами: их смотрят разработчики и SRE.

### Dashboard as code / дашборд как код

Зрелый подход. Дашборды не рисуют мышкой в UI, а хранят в Git как JSON. Накатывают через API при деплое. Подробнее о создании и редактировании: раздел Dashboards Classic → [Create and edit dashboards](https://docs.dynatrace.com/managed/analyze-explore-automate/dashboards-classic/dashboards/create-dashboards).

*Что это даёт.*
- Версионирование: видно, кто и когда менял.
- Ревью: изменения едут через pull request, коллеги смотрят перед накатом.
- Одинаковые дашборды в dev / test / prod: не надо руками переносить.

В банке это требование compliance. Любое изменение в production должно быть прослежено через change-management. Ручные правки в UI боевого окружения: нарушение процесса.

### Management Zone и дашборды

**[Management Zone](https://docs.dynatrace.com/managed/shortlink/management-zones) / зона управления**: способ поделить данные Dynatrace на куски по принадлежности (команде, сервису, бизнес-линии). Выбрал в верхнем фильтре zone «Retail Banking»: все виджеты всех дашбордов автоматически показывают только данные этой зоны. По умолчанию в окружении до 5 000 management zones. <!-- last-verified: 2026-04-27 source: docs.dynatrace.com/managed/shortlink/management-zones -->

*Полезная практика: один дашборд на несколько команд.* Команда retail переключает zone «Retail» и видит своё. Команда corporate переключает «Corporate» и видит своё. Дашборд один, контекст у каждого свой. Меньше дублирования, проще поддерживать.

### Air-gapped контекст

Всё работает одинаково, особенностей нет. Дашборды хранятся в кластере, данные приходят с агентов внутри контура. Единственное: в **Allowed URL pattern rules** не имеет смысла класть внешние домены: интернет всё равно недоступен, а внутренние ресурсы (Confluence, файловое хранилище) доступны напрямую.

### Ключевые термины

- **Dashboard / дашборд / панель мониторинга**: страница с виджетами.
- **Widget / виджет / плитка**: один элемент на панели.
- **Preset / пресет / встроенный дашборд**: готовая панель из коробки.
- **Clone / клонирование**: копия пресета для редактирования.
- **Pin to dashboard**: добавить виджет из Data Explorer прямо на панель.
- **Dashboard as code**: хранить JSON дашбордов в Git и накатывать через API.
- **Home dashboard**: стартовая страница пользовательской группы при входе.
- **Anonymous access**: публичная ссылка на дашборд без логина.
- **Management Zone / зона управления**: сегментация данных по принадлежности.

## 📝 Практика (3 минуты; на demo-тенанте аккаунт read-only, поэтому в предпросмотре без сохранения)

Собрать «дашборд одного взгляда» в порядке «сначала общий статус, потом где именно плохо»:

1. **Observe and explore → Dashboards** → Create dashboard (на демо дашборд не сохранится: жёлтая плашка про write permissions; на вашем Managed эта же кнопка сохранит).
2. Плитка списка проблем (всё ли хорошо).
3. Из Data Explorer: график CPU по хостам `easytravel*` → Pin to dashboard (где именно плохо).

Что должно получиться: понимание порядка сборки и приём «фильтр по тегу вместо перечисления хостов»: дашборд, собранный по тегу, сам подхватывает новые хосты и не устаревает (подробно: тема «Автотеги»).
