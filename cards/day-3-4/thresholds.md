## ГДЕ
Пять экранов Settings → Anomaly detection для приложений.
Web: RUM Web applications, route `/ui/settings/builtin:anomaly-detection.rum-web`.
Mobile: RUM Mobile applications, route `/ui/settings/builtin:anomaly-detection.rum-mobile`.
Custom: RUM Custom applications, route `/ui/settings/builtin:anomaly-detection.rum-custom`.
Crash rate вынесен в два отдельных экрана: custom `/ui/settings/builtin:anomaly-detection.rum-custom-crash-rate-increase`, mobile `/ui/settings/builtin:anomaly-detection.rum-mobile-crash-rate-increase`.

## ЗАЧЕМ
Эти экраны задают пороги для клиентских приложений (web, mobile, custom) в RUM: когда Davis AI заводит Problem по деградации ключевых метрик, падению или росту трафика, росту failure rate и росту crash rate.
Настройка прямо определяет баланс «скорость реакции против шума» и насколько быстро дежурный узнает о проблеме на стороне клиента.

## ЦИФРЫ
- 4 типа аномалий приложения: деградация ключевых метрик user actions, падение трафика, рост трафика, рост failure rate.
- Два режима на каждый тип: automated baselining (Davis AI учится на реперном периоде, по умолчанию последние 7 дней) или fixed thresholds с уровнями чувствительности Low / Medium / High.
- Failure rate в automated baselining задаётся двумя порогами: относительный в % (на сколько процентов выросла доля ошибок) и абсолютный в % (выше какой доли ошибок это уже проблема). Пример, не значения по умолчанию: относительный 50%, абсолютный 3%, базовый уровень 2%, при росте доли ошибок до 3,5% нарушены оба (рост на 75% и выше 3%), при росте до 2,8% относительный порог не нарушен (рост 40%, ниже 50%), Problem нет.
- Crash rate это отдельный детектор: baseline по версии приложения, чувствительность Low / Medium / High; точные окна наблюдения и минимум трафика в публичной доке не зафиксированы.
- Crash rate = (crashes / sessions) × 100.
- Перцентили важнее среднего: медиана времени загрузки может быть 200 мс, а хвост P99 до 5 секунд у пользователей со слабой сетью или старыми устройствами.

## ЕСЛИ→ТО
- ЕСЛИ доля ошибок нарушила оба порога сразу, и относительный, и абсолютный → ТО Davis заводит Problem; нарушен только один из двух → Davis молчит, это защита от ложных срабатываний.
- ЕСЛИ для fixed thresholds выбран Low → ТО применяется высокая статистическая уверенность: кратковременный скачок нагрузки Problem не заведёт, шума меньше, но о деградации дежурный узнает позже.
- ЕСЛИ выбран High → ТО статистическая уверенность не применяется: каждое нарушение порога заводит алерт, реакция мгновенная, ложных срабатываний больше.
- ЕСЛИ на версии приложения совсем мало одновременных пользователей → ТО crash-rate event может не подняться: защита от ложного алерта на низком трафике (конкретный минимальный порог трафика в публичной доке не зафиксирован).

## ЗАПАСНОЙ ПЛАН
Страницы порогов на демо серые (нет write-прав): это ожидаемо, показываю снимки из курса и проговариваю механику на экране web-приложений.
Точные дефолтные проценты порогов по памяти не называю, отсылаю к значениям на самой странице тенанта; числа failure-rate из примера (относительный 50%, абсолютный 3%) проговариваю как иллюстрацию, а не как значения по умолчанию.
Ключевой экран для показа: web-приложения, на нём объясняю два порога сразу и уровни Low / Medium / High; crash rate показываю на экране mobile.

## ВОПРОСЫ АУДИТОРИИ
- «Почему для Problem нужны оба порога, а не один?» Ответ: это защита от ложных срабатываний, Problem заводится только когда доля ошибок нарушила и относительный, и абсолютный порог, нарушение одного молчит.
- «Чем crash отличается от обычной ошибки?» Ответ: при обычной ошибке (JS exception, network error) пользователь продолжает работу, а crash это аварийное падение (необработанное исключение, OOM, segfault), пользователь вынужден перезапустить приложение.
- «Где считаются пороги и baseline в закрытом контуре?» Ответ: локально в кластере на данных от RUM-сниппетов и Mobile SDK, без внешних сервисов.
