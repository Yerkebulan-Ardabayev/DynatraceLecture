## ГДЕ
Список проблем: Observe and explore → Problems, route `/ui/problems`.
Карточка одной проблемы: клик по строке в списке, route `/ui/problems/<P-NNNNNNNN>`.
Из строки два перехода: Affected (затронутая сущность, «где болит») и Root cause (первопричина по Davis, «где чинить»), оба ведут прямо в карточку сущности мимо карточки проблемы.

## ЗАЧЕМ
Тема не про саму страницу Problems (её разбирали в Дне 1), а про то, как из карточки проблемы быстро провалиться в затронутые сущности: сервис, хост, процесс, БД, приложение.
Это основной путь дежурного инженера: от инцидента к метрике, трейсу или логу через один объект, а не через глобальный поиск.

## ЦИФРЫ
- На демо-тенанте 71 активная проблема, в списке видно 50 (у вашего тенанта цифры могут быть другими).
- Пример строки: Http monitor local outage P-26049005, Impacted easytravel storebooking, Root cause EasytravelService, длится 10 минут.
- Пример алерта БД: Postgres Availability P-26049003, RDS-инстанс на порту 5432, длится 16 минут.
- Alerting profile сводит проблему по трём scope через AND: Management zones + Severity rules (до 100, между ними OR) + Event filters (до 20).

## ЕСЛИ→ТО
- ЕСЛИ две аномалии совпали только по времени → Davis не склеивает их сразу: сначала проверяет реальную зависимость в топологии, есть зависимость → одна Problem с общим корнем, лишние алерты не плодятся.
- ЕСЛИ Affected и Root cause различаются → чиним по Root cause, симптом смотрим в Affected; в простых случаях они совпадают.
- ЕСЛИ колонка Root cause пустая → Davis честно говорит «данных мало» (инфра без OneAgent, внешний SaaS или новая технология без baseline), причину инженер определяет по графу сущностей.
- ЕСЛИ проблема критичная, а Alerting profiles пусто → она не ушла ни в одну интеграцию, дежурный о ней не знает, нужно разобраться почему.

## ЗАПАСНОЙ ПЛАН
Если живой список Problems пуст или тенант недоступен: показываю снимок из курса, по нему проговариваю колонки Problem, Impacted, Affected, Root cause, Alerting profiles и два пути из строки (клик по строке → карточка проблемы, клик на Affected или Root cause → сразу карточка сущности).
Если карточка проблемы не раскрывается: разбираю её по снимку по зонам, верх (имя, ID, статус), центр (граф затронутых сущностей: красные пострадали, жёлтые затронуты, зелёные соседние без нарушений), низ (лента событий со ссылками на графики); дословные блоки живой карточки (Business impact analysis, Root cause, Visual resolution path, Comments) сверены 2026-07-28.
Прыжки в PurePath и логи показываю только там, где на сущности есть трейсы и включен Log Monitoring, иначе проговариваю словами.

## ВОПРОСЫ АУДИТОРИИ
- «Чем Affected отличается от Root cause?» Ответ: Affected это «где болит» (сущность с деградацией, её симптомы видит пользователь), Root cause это «где чинить» (сущность-первопричина, её восстановление вернёт всех зависимых); в простых случаях они совпадают.
- «Почему колонка Root cause иногда пустая?» Ответ: Davis не набрал данных для вывода, обычно это инфра без OneAgent, внешний SaaS или новая технология без baseline, тогда причину определяют по графу сущностей вручную.
- «Работает ли эта навигация в закрытом контуре?» Ответ: да, workflow одинаков с облаком, данные переходов полностью локальные, наружу ничего не уходит, а из внутреннего Jira или Slack переход в интерфейс идёт по внутренней ссылке.
- «На каком шаге спуска вы остановитесь и передадите дальше?» Ответ на обсуждение: первая линия обычно доводит до Root cause и имени первопричинной сущности (этого хватает для маршрутизации тикета), инженер сопровождения спускается дальше: до конкретного запроса, метода или хоста.
