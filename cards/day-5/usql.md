## ГДЕ
Основной вход: Application Observability → Frontend → User sessions query, route `/ui/user-sessions/query`.
Те же запросы доступны ещё двумя путями: REST-endpoints `/table` (плоский результат) и `/tree` (иерархический) с API-токеном; отдельный USQL-запрос встраивается в Data Explorer как tile на дашборд.

## ЗАЧЕМ
USQL (User Session Query Language) это SQL-подобный язык по пользовательским сессиям и user actions: отвечает на вопросы, которые готовые дашборды не закрывают (разбивка проблемных сессий по версии приложения, по локации, по доле network error).
Managed-акцент: для сессий это штатный рабочий инструмент контура. DQL и Grail, которыми в SaaS-документации решают те же задачи, в air-gapped Managed отсутствуют. <!-- qc:ignore=SAAS -->

## ЦИФРЫ
- Четыре виртуальные таблицы: usersession (строка на сессию), useraction (строка на действие), userevent (события, page changes и rage), usererror (ошибки и crashes).
- Default LIMIT 50 строк, максимум поднимается до 5000, выше нельзя.
- Распределение UX-скоров собирается запросом: (203 + 0.5 × 52) / 278 = 0.824 по формуле Apdex; это session-level score, у Apdex карточки приложения action-level пороги, числа могут не совпасть.
- Запрос с 11 и более LIKE-условиями, где wildcard стоит не в конце, USQL отклоняет.
- Глубина истории по сессиям ограничена retention Sessions Classic: 35 дней.
- USQL-запрос как tile на дашборде пересчитывается каждые 5 минут.

## ЕСЛИ→ТО
- ЕСЛИ по привычке из SaaS набрать DQL → в Managed запрос не пойдёт: DQL живёт поверх Grail, а Grail в air-gapped контуре нет, для сессий язык это USQL. <!-- qc:ignore=SAAS -->
- ЕСЛИ ждёте в выборке текущую живую сессию → её там не будет: USQL считает только закрытые сессии.
- ЕСЛИ забыть LIMIT → вернётся дефолтные 50 строк, а на попытке вытащить тысячи строк UI виснет на рендеринге; поднимаем LIMIT до 5000, не выше.
- ЕСЛИ нужно сравнить два поля одной строки между собой → USQL так не умеет, оба значения считаем и сравниваем уже в скрипте.

## ЗАПАСНОЙ ПЛАН
Если редактор не открывается или запрос не отдаёт результат: показываю снимок User Session Query из курса, проговариваю три части экрана (текст запроса, кнопки Run query и Copy, таблица результата) и разбираю готовый пример `SELECT userExperienceScore, count(*) FROM usersession GROUP BY userExperienceScore`.
Если кто-то тянется к DQL: сразу говорю, что запросы к сессиям в Managed идут на USQL, а Grail и DQL это SaaS, здесь их нет. <!-- qc:ignore=SAAS -->
Историю глубже 35 дней по сессиям не обещаю: для долгого хранения показываю связку через API-экспорт `/table` во внешний BI.

## ВОПРОСЫ АУДИТОРИИ
- «Почему у нас нет DQL и Grail, как в документации?» Ответ: DQL работает поверх Grail, это SaaS-хранилище; в air-gapped Managed его нет, запросы к сессиям пишем на USQL. <!-- qc:ignore=SAAS -->
- «Можно ли за один запрос соединить usersession и useraction?» Ответ: нет, USQL это одна таблица на SELECT, JOIN-ов между таблицами нет; берём нужную таблицу и фильтруем.
- «Почему свежая сессия не попала в отчёт?» Ответ: USQL считает только закрытые сессии, живая ещё идёт и в выборку не входит.
