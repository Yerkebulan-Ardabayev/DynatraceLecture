## ГДЕ
Два живых экрана. Список сессий с фильтрами воронки: Application Observability → Frontend → User sessions, route `/ui/user-sessions`.
USQL для funnel и path analysis: Frontend → User sessions query, route `/ui/user-sessions/query`.

## ЗАЧЕМ
Journey это реальный путь одного пользователя: открываю сессию, вижу хронологию user actions, нахожу точку боли (например rage click на кнопке оплаты).
Funnel это та же дорога с подсчётом, сколько сессий прошло каждый шаг и где утекают деньги. Оба инструмента входят в DEM.

## ЦИФРЫ
- Без фильтра User sessions отдаёт только первые сессии по времени старта, нужная теряется в общей массе.
- Conversion goals: максимум 20 на приложение; без заведённой цели колонка Conversions пустая.
- USQL: по умолчанию 50 строк, максимум через LIMIT 5000; видит только закрытые сессии, live не учитывает.
- User action naming rules: до 250 правил на приложение и до 50 пользовательских placeholder'ов.
- Пример funnel: из 5000 сессий корзина 1200, checkout 800, оплата 450, успех 420; главная утечка между checkout и Pay (у вашего тенанта цифры могут быть другими).
- Типовая норма funnel входа в ДБО 80-90%, перевода средств 70-80%; падение ниже 50% это инцидент.

## ЕСЛИ→ТО
- ЕСЛИ задать условие сегмента (Converted: No плюс Application type: Web) → в списке остаются только нужные сессии; ЕСЛИ фильтр не задавать → отдаётся весь трафик первыми сессиями списка, и нужную теряешь в массе.
- ЕСЛИ в настройках приложения заведена conversion goal → сессия помечается converted и фильтры Converted и Conversion goal её отбирают; ЕСЛИ цель не заведена → отделить «дошёл до цели» от «ушёл» нечем.
- ЕСЛИ имена действий не нормализованы → одно действие через разные элементы или языки дробится на разные имена и счётчик шага размазывается; ЕСЛИ настроены naming rules → варианты сводятся в одну группу и шаг funnel считается как одно действие.
- ЕСЛИ пользователь завис на шаге funnel → end-to-end tracing через заголовок x-dynatrace показывает не только факт задержки, а конкретный backend-сервис и SQL-запрос под ним.

## ЗАПАСНОЙ ПЛАН
Если список сессий пуст: открываю снимок User sessions из курса, разбираю фильтр Conversions and bounces на примере (сессия без конверсии на странице оплаты → хронология user actions → rage click на кнопке «Оплатить»).
Готовой Funnels-диаграммы в air-gapped Managed нет (это SaaS Apps): воронку собираю через USQL, по одному запросу на каждый шаг и сравнению чисел; визуальную воронку строю custom-dashboard через Dynatrace API или внешним BI (Grafana, Power BI).
Если USQL-редактор пуст или без прав: проговариваю пример funnel по снимку курса и напоминаю, что USQL видит только закрытые сессии.
Лекторский сценарий: workshop/day-3.md, блок [1:10-1:25] «USQL: запросы к сессиям». <!-- qc:ignore=CARD_UNSOURCED_NUMBER -->

## ВОПРОСЫ АУДИТОРИИ
- «Чем journey отличается от funnel?» Ответ: journey это абстрактная карта поведения без цифр (для проектирования экранов), funnel это жёсткая последовательность шагов с подсчётом прохождения (для операционки, где теряются деньги).
- «Почему funnel через USQL, а не готовая диаграмма?» Ответ: Apps-формат Funnels относится к SaaS-стэку и в air-gapped Managed не активен, в Classic UI шаг funnel считается запросом USQL и сравнением чисел, визуальную воронку строят через API или внешний BI.
- «Пользователь начал в мобильном, продолжил в web, почему две сессии?» Ответ: по умолчанию кросс-приложения journey считаются разными сессиями, чтобы связать нужен user-ID tagging через RUM JavaScript или Mobile SDK API (стабильный userId, который видит и web, и mobile).
