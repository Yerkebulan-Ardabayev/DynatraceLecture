### [0:05-0:20] Зачем RUM + заведение приложений

**Цель:** продать боль «у меня не воспроизводится» и научить заводить приложения правилами Application detection, не трогая служебное My web application.

**Подводка:** Классика жанра: пользователь звонит «у меня всё медленно и ошибки», инженер отвечает «у меня не воспроизводится». Чтобы разобраться, вам нужен DevTools в браузере пользователя, а его вам никто не откроет. RUM это и есть DevTools чужого браузера, легально и для всех пользователей сразу. Технически это JS-агент: маленький скрипт на странице, как счётчик веб-аналитики вроде Яндекс.Метрики, только смотрит он не маркетинговые клики, а техническое здоровье: время загрузки, ошибки, запросы к бэкенду.

**Демо:**
1. Левое меню → **Digital Experience** → **Web**: список веб-приложений (соответствие пункта Web этому списку: не сверено; сам экран списка в снапшоте есть, URL `/ui/applications`). Показать `www.angular.easytravel.com`; рядом в пункте **Mobile** живёт `easyTravel Mobile`.
2. Вопрос себе вслух: а откуда Dynatrace знает, что этот трафик и есть «приложение»? Идём в правила: левое меню → **Manage** → **Settings** → группа **Web and mobile monitoring** → экран **Application detection** (заголовок на экране: **Define application detection rules**; имя пункта в списке группы: не сверено). URL: `/ui/settings/builtin:rum.web.app-detection`.
3. Пройтись по списку правил курсором: каждое правило матчится по URL, сверху вниз, побеждает первое совпавшее. Показать, где добавляется новое правило (кнопка: не сверено).
4. Подсветить инструмент проверки правил Check your existing detection rules: вводим URL, видим, какое правило сработает (наш курс, app-detection; вид на экране: не сверено).
5. Типовая ошибка новичка: взять дефолтное **My web application** и переименовать его в «наш портал». Нельзя: это служебный контейнер для трафика, который не подошёл ни под одно правило. Его не переименовываем и не удаляем, в него заглядываем и разносим трафик правилами по настоящим приложениям.

**Как найти (если забыл дорогу):** левое меню → **Manage** → **Settings** → **Web and mobile monitoring** → Application detection. Запасной способ: глобальный поиск по словам «Application detection» (поле «Search <имя окружения>...» в верхней панели).

**Тезисы:**
- Правила оцениваются сверху вниз, срабатывает первое совпавшее, дальше обработка останавливается; лимит: до 1000 правил на окружение (наш курс, app-detection).
- Best practice: дробите сайт на приложения по зонам ответственности. У каждого куска свой владелец, свои метрики, свой Apdex. Одно приложение «весь портал» это средняя температура по больнице.
- My web application: служебная копилка несматченного трафика. Регулярно заглядывать и разбирать, но не переименовывать (наш курс, app-segments).
- Правил обычно нужно немного: 3-10 на организацию, по числу реальных веб-приложений (наш курс, app-detection).

**Вопрос в зал:** ваш портал: на сколько приложений вы бы его разбили и по какому признаку: по доменам, по командам, по контурам?

**Практика:** на бумаге: напишите правило для своего главного домена: что в поле URL, какое имя приложения. Через минуту два человека зачитают.

**Переход:** Это что касалось определения приложений. Теперь смотрим, что приложение нам даёт.

### [0:20-0:40] Карточка приложения www.angular.easytravel.com

**Цель:** научить читать карточку приложения: производительность, Apdex, браузеры и роботы, география, три типа действий, ошибки.

**Подводка:** Предлагаю провалиться в само приложение и посмотреть на него глазами владельца. Здесь один экран отвечает сразу на три вопроса: быстро ли у нас, у кого именно медленно и что конкретно ломается.

**Демо:** (внутренности карточки приложения снапшотом не подтверждены: весь блок помечаю (не сверено), состав блоков сверить на пре-флайте)
1. Из списка **Web** открыть `www.angular.easytravel.com` (не сверено).
2. Производительность и Apdex: показать общий скор и динамику. Проговорить: здесь средняя температура по всему приложению, дальше будем спускаться до конкретики.
3. Браузеры и роботы (не сверено): разбивка по браузерам, отдельно роботы и синтетика. Заметить вслух: роботов из статистики пользователей надо мысленно вычитать.
4. Геокарта (не сверено). Честная оговорка, обязательно: приложение демонстрационное, трафик оно генерирует само и IP-адреса у него синтетические, поэтому карта выглядит странно и по регионам мы сегодня не покликаем. На вашей инсталляции с живыми пользователями карта кликабельна до города.
5. Три типа действий: Load, XHR, Custom. XHR объяснить бытовым примером: личный кабинет, нажали кнопку, страница не перезагрузилась, а данные подъехали: вот это XHR-действие.
6. Ошибки (не сверено): JavaScript-ошибки и сетевые отказы. Подсветить связку: действие с JS-ошибкой автоматически падает в Frustrated, даже если оно быстрое.
7. Типовая ошибка новичка: смотреть на среднее время. Вспоминаем вчерашнее: кто-то ест капусту, кто-то мясо, в среднем все едят голубцы. Работаем по медиане и перцентилям.

**Как найти (если забыл дорогу):** левое меню → **Digital Experience** → **Web** → клик по имени приложения. Запасной способ: глобальный поиск по имени приложения (поле «Search <имя окружения>...» в верхней панели).

**Тезисы:**
- Apdex считается от порога T, который задаёте вы: действие быстрее T это Satisfied, от T до 4T это Tolerating, дольше 4T это Frustrated (наш курс, ux-metrics).
- Формула: Apdex = (Satisfied + 0.5 × Tolerating) / Total; шкала из пяти уровней: Excellent 0.94-1.0, Good 0.85-0.94, Fair 0.7-0.85, Poor 0.5-0.7, Unacceptable ниже 0.5 (docs.dynatrace.com/managed/observe/digital-experience/rum-concepts/scores-and-ratings/apdex-ratings).
- Действия с JavaScript-ошибками попадают в Frustrated независимо от времени отклика (наш курс, ux-metrics). Поэтому Apdex ловит не только «медленно», но и «сломано».
- Типы действий: Load это загрузка страницы по URL, XHR это запросы без перезагрузки страницы, Custom размечают разработчики через JS API (наш курс, rum).
- Пороги Apdex настраиваются: для внутренних систем в локальной сети пороги обычно ужесточают, для публичных сайтов оставляют мягче (наш курс, ux-metrics).

**Вопрос в зал:** для вашего внутреннего портала какой порог T вы бы поставили: секунду, две, три? И почему.

**Практика:** прямо сейчас, 2 минуты: в карточке приложения найдите, какой из трёх типов действий самый медленный за сегодня. Ответ одним словом в чат.

**Переход:** Окей, приложение целиком посмотрели. Но приложение состоит из людей. Пойдём смотреть на конкретного человека.

### [0:40-1:00] Сессии: провал, водопад, «в один клик», Session Replay

**Цель:** пройти путь «список сессий → сессия человека → водопад действия → бэкенд-трассировка в один клик» и показать Session Replay с маскированием. Это кульминация дня.

**Подводка:** Сессия это биография визита: один человек, один заход, все его действия по порядку. Сейчас найдём живого пользователя и прочитаем его визит как сюжет. А в конце покажу возможность, ради которой RUM вообще покупают.

**Демо:**
1. Левое меню → **Digital Experience** → **Session Segmentation**. Ремарка лектору, единственная на весь день: поверх части экранов SaaS-тенанта висят баннеры новых интерфейсов; вслух не читаем и не цитируем: баннер игнорируем, в Managed его нет.
2. Показать фильтры сегментации (состав фильтров: не сверено). Найти тегированных пользователей: maria или Tatjana Jonker (имена с тенанта, ui_elements). Проговорить: тегированный пользователь это когда приложение сообщает нам логин; без тега пользователь виден как Anonymous с идентификатором.
3. Провалиться в сессию (переход и вид карточки сессии: не сверено). Прочитать шапку: ОС, браузер, география, длительность. Дальше прочитать действия как сюжет: вот человек искал тур, вот открыл результаты, вот здесь споткнулся.
4. Открыть водопад действия (не сверено): это DevTools, только DevTools пользователя мы доступа не имеем, зато можем посмотреть его сессию через призму водопада. Показать фазы: сеть, сервер, рендеринг, ресурсы.
5. Кульминация. Внутри действия найти переход к серверной стороне (кнопка/ссылка: не сверено) и произнести: самая крутая возможность: мы в один клик уходим из браузера пользователя в бэкенд-трассировку. Вот действие, вот клик, вот трассировка, вплоть до SQL-запроса. В один клик от жалобы «у меня медленно» до строчки, которая медленно работает. Запомните это «в один клик»: это главный аргумент, почему RUM и бэкенд-мониторинг должны жить в одной системе.
6. Session Replay: левое меню → **Digital Experience** → **Session Replay**. Фильтр записей: на экране есть переключатель Session replay: Yes (ui_elements: кнопка «Session replayYes»). Наличие записей на таймфрейме: требование пре-флайта. Открыть запись (плеер: не сверено).
7. Проговорить честно: это видеозапись в кавычках. Никакого видео нет: записывается взаимодействие с DOM, потом последовательность воспроизводится как кино.
8. Маскирование и приватность: показать словами (экран настроек маскирования: не сверено), режимы перечислить по тезисам ниже.
9. Типовая ошибка новичка: делать выводы по live-сессии. Она ещё дозаписывается: сначала дождитесь завершения, потом анализируйте.

**Как найти (если забыл дорогу):** левое меню → **Digital Experience** → **Session Segmentation**; записи: **Digital Experience** → **Session Replay**. Запасной способ: глобальный поиск по слову «Session» (поле «Search <имя окружения>...» в верхней панели).

**Тезисы:**
- Веб-сессия завершается после 30 минут бездействия, мобильная после 10 минут (наш курс, sessions). Пауза дольше таймаута: старая сессия закрывается, заводится новая с новым идентификатором (наш курс, rum).
- Если сессия накапливает порядка 200 действий, она автоматически разрезается на части (наш курс, sessions). Не пугайтесь «коротких» кусков у очень активных пользователей.
- Живая сессия со значком live ещё не финальная: она дозаписывается, закрывшаяся сессия может финализироваться с задержкой (наш курс, rum). Выводы делаем по завершённым.
- Session Replay: четыре режима маскирования: Mask all, Mask user input, Allow list, Block list (наш курс, session-replay).
- Маска на записи означает, что чувствительные данные физически не попадают в кластер; маска только на воспроизведении означает, что данные в кластере есть, а скрывает их плеер, и пользователь с правом Replay sessions without masking увидит всё (наш курс, session-replay). Для банковского контура выбираем маску на записи.
- Перед включением Replay согласуйте с безопасностью и юристами состав записываемого: это персональные данные.

**Вопрос в зал:** первый: что вы видите в сессии такого, чего нет ни в одном серверном логе? Второй: какие поля вашего фронта вы замаскируете первыми?

**Практика:** найдите любую сессию с ошибкой и скажите одной фразой, что пользователь делал прямо перед ней. 3 минуты, ответы в чат.

### [1:00-1:10] Перерыв

**Цель:** отдых зала, буфер на отставание от тайминга.

### [1:50-2:05] Кастомное оповещение: три простых шага

### [2:15-2:22] API и токены

**Цель:** показать, где живут токены доступа, зачем нужен API и как выглядит типовой сценарий интеграции в закрытом контуре.

**Подводка:** Всё, что мы делали мышкой, умеет делать API: забирать метрики, читать проблемы, создавать дашборды. Ключ к API это токен. Покажу, где токены выдаются и как выглядит правильная гигиена.

**Демо:**
1. Левое меню → **Manage** → **Access Tokens** (`/ui/access-tokens`). Показать таблицу: колонки Token name, Last used, Created, Number of scopes (ui_elements).
2. Нажать **Generate new token** (кнопка подтверждена, ui_elements): показать выбор scope (список scope: не сверено). Проговорить принцип: токен на интеграцию, scope строго минимальные: интеграция читает метрики, значит только чтение метрик.
3. Пример сценария интеграции, словами поверх экрана: скрипт каждые 30 секунд опрашивает открытые проблемы через API и постит новые в ваш мессенджер: pull-модель, которая работает, даже когда исходящие соединения от кластера ограничены (наш курс, api).
4. Показать заголовок авторизации на слайде или в блокноте: Authorization: Api-Token и дальше сам токен (наш курс, api). Секретную часть токена нигде не показывать: показываем токен только в момент генерации на тестовом scope и сразу удаляем.
5. Упомянуть пункт **Personal access tokens** (пункт меню подтверждён, ui_elements; `/ui/personal-access-tokens`): токены, привязанные к учётной записи пользователя (формулировку сверить по managed-доке на пре-флайте; содержимое экрана: не сверено).
6. Типовая ошибка новичка: один «токен на всё» с полными правами, розданный всем скриптам. При утечке придётся ротировать всё сразу.

**Как найти (если забыл дорогу):** левое меню → **Manage** → **Access Tokens**; персональные: соседний пункт **Personal access tokens**. Запасной способ: глобальный поиск по «tokens» (поле «Search <имя окружения>...» в верхней панели).

**Тезисы:**
- Токен состоит из трёх частей: префикс, публичная часть, секретная часть; публичная часть 24 символа, секретная 64 (наш курс, api). Публичную можно светить в логах для идентификации, секретная охраняется как пароль.
- Классические Environment-токены носят префикс dt0c01, в таблице префиксов документации API-токен обозначен dt0s01: не путайтесь, при разборе инцидентов префикс подскажет тип токена (наш курс, api).
- Один сценарий = один токен с минимальными scope; утечка одного токена не кладёт все интеграции.
- Типовые применения API в закрытом контуре: выгрузка метрик во внешний портал, pull-опрос проблем для мессенджера, накатка дашбордов из Git (наш курс, api).

**Вопрос в зал:** какая ручная операция у вас повторяется так часто, что её первой стоит перевести на API?

**Практика:** запишите этот сценарий одной строкой: он пригодится завтра, на прикладном дне.
