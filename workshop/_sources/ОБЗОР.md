## Ключ Астром ↔ Dynatrace (карта соответствий)

Платформа повторяет классический Dynatrace (не новый Grail/DQL, а «старый» стек Managed). Соответствия, всплывшие в курсе:

| Ключ Астром | Dynatrace |
|---|---|
| Единый агент | OneAgent |
| Активный шлюз кластера / активный шлюз среды | ActiveGate (cluster / environment) |
| Проблема + ИИ-движок + root cause | Davis AI + Problems |
| Зоны управления | Management Zones |
| USQL (UserSession/UserAction/UserEvent/UserError) | USQL (тот же язык) |
| Базовые линии + аномалии | Automatic baselining + anomaly detection |
| Воспроизведение сеанса | Session Replay |
| Apdex | Apdex |
| Атрибуты запросов | Request Attributes |
| Расширения (Python, на шлюзе среды) | ActiveGate / Extensions |
| Модуль безопасности приложений | Application Security |
| Синтетика (браузерный и HTTP-монитор) | Synthetic Monitoring |
| Лицензия «внешние источники данных» (ВИД) | DDU (Davis Data Units) |
| Кластер: Cassandra (метрики) + Elasticsearch (логи+RUM) + сырые данные на ФС | Dynatrace Managed cluster (та же архитектура) |
| Развёртывание: SaaS / управляемая / офлайн | SaaS / Managed / (air-gapped Managed) |

Важное отличие акцента: у клиента самый востребованный вариант, это **полностью офлайн** (air-gapped) инсталляция, обновления пакетами с сервера обновлений. Это ровно тот же контур, что и Dynatrace Managed в закрытом периметре.

## День 1, часть 1 — Архитектура: кластер, шлюзы, единый агент, обзор интерфейса

**Суть.** Вводное занятие: варианты развёртывания, устройство кластера и хранилищ, активные шлюзы, как работает единый агент и его накладные расходы, затем живой обзор интерфейса и модели топологии.

**Ключевое:**
- Три варианта инсталляции: SaaS (кластер у вендора), управляемая/Managed (кластер в периметре клиента + линк к вендору за лицензиями и обновлениями), полностью офлайн (всё в периметре, без линков; названа самой востребованной).
- Кластер: ноды, отказоустойчивость, рекомендация **от 4 нод** из-за Cassandra с фактором репликации 3; горизонтальное масштабирование.
- Компоненты ноды: Java-ядро, хранилища (Elasticsearch = логи + пользовательские сессии; Cassandra = метрики, хранение до 5 лет; хранилище сырых данных на ФС = трассировки, данные уровня кода), Nginx (внутренняя балансировка), внутренний шлюз.
- Активные шлюзы: **кластерный** (публичный эндпоинт, приём трафика агентов/мобильных/синтетики) и **шлюз среды** (внутренний сбор трафика агентов в подсети + среда запуска расширений).
- Расширения: Python-мини-программы (Postgres, MongoDB, Kafka, SSH…), работают на шлюзе среды, есть SDK.
- Единый агент: автообнаружение и внедрение в технологии (нативные интерфейсы вроде JVM TI + инъекция библиотек через LD_PRELOAD); поддержка Java, .NET, Go, Python, PHP, Node.js, Nginx.
- Оверхед агента ≈ 400-500 МБ RAM, влияние на приложение минимальное при правильной настройке.
- Живой обзор интерфейса: панель навигации, выбор окружения, зоны управления, Time Frame Selector, кнопки проблем и уязвимостей. Топология по уровням: дата-центры → хосты → процессы → сервисы → приложения (демо: дата-центр Казань, хост Easy Travel с проблемой CPU).

**Практика:** минимально стабильный кластер = 4 ноды; сырые данные не реплицируются и не бэкапятся (при потере ноды теряются навсегда); кластер не выставлять в публичную сеть; оверхед на Kubernetes/OpenShift считать отдельно; уровень дата-центров задаётся вручную по IP-диапазонам; синтаксис таймфрейма «-15m», «?» открывает справку.

**Оговорки транскрипта:** имя продукта постоянно искажается («ключа стром / ключ-остром» = Ключ Астром); порты «4.9»/«4.43» искажены (по Dynatrace-аналогии вероятно 9999 для шлюза и 443/8443 для кластера, но по тексту не подтверждается, сверить с докой); домен доки не читается точно.

## День 1, часть 2 — Сквозной обзор сущностей, установка агента, метрики, базовые линии

**Суть.** Прогон по интерфейсу снизу вверх: страницы хоста, процесса, сервиса, приложения. Режимы агента и лицензирование, два способа мониторинга веб-приложений и мобильных, установка агента, работа с метриками и визуализацией, механика базовых линий и аномалий.

**Ключевое:**
- Страница хоста: режим агента, зоны управления, теги, доступность, метрики; вкладки процессов (зелёная галочка = инструментирован), дисков (IOPS), сети, контейнеров, памяти, событий, логов.
- Режимы агента: **full stack** (лицензия по объёму RAM) против **только инфраструктура** (потолок 0,3 лицензии, root cause всё равно сохраняется).
- Теги: ручные против авто-правил; настойчиво повторяется как главный best practice, тегировать всё на всех уровнях.
- Страница процесса (демо easyTravel Apache): взаимодействия, трафик, стандартные + технологические метрики.
- Страница сервиса: 3 базовые метрики (время отклика, fail rate, пропускная способность) + 4-я (CPU на запрос) при полной инструментации.
- Мониторинг веб-приложений: автоматический (агент на веб-сервере внедряет JS-агента, полная цепочка фронт-бэк, без CORS) против ручного (вставка JS-кода как Яндекс.Метрика, теряется связка фронт-бэк).
- Мобильные: мастер инструментирования (Android/iOS/tvOS/гибрид, библиотека + идентификатор + URL в build.gradle).
- Установка единого агента: токен, две команды, перезапуск помеченных процессов.
- Метрики (демо: 874 метрики): префиксы build-in/custom/ext, агрегации; инструмент визуализации (сортировка, фильтр, rate, time shift, арифметика, экспорт CSV/API, типы графиков, визуальные пороги).
- Базовые линии и аномалии.

**Практика (конкретные цифры):** лицензирование по RAM (16 ГБ = 1 лицензия, 32 = 2, 64 = 4; 8 ГБ = 0,5); режим «только инфраструктура» ≤ 0,3 лицензии; базовая линия формируется полностью ≈ за **7 дней**; аномалия срабатывает, когда метрика вышла за коридор и зафиксирована вне зоны **3 замера за 5 минут**, тогда ИИ поднимает проблему; визуальные пороги на графике не создают оповещений (только для глаза); порог события по диску «меньше 15% свободного места».

**Оговорки:** «слоу/сервис level объект» = SLO; «slow put» = throughput; «ICT внутри ключа» = ИИ-движок (Davis-аналог); «ld-прилог» = LD_PRELOAD; ближе к концу whisper вырождается в «Вот. Вот.» (артефакт, содержания нет). Реальная речь до ~1:22, дальше тишина (норма).

## День 2, часть 1 — Карточка проблемы и разбор root cause; что такое сервис, мониторинг БД, метрики и агрегации

**Суть.** Как из аномалии рождается «проблема» (единая карточка со всеми взаимосвязями и корневой причиной), разбор анатомии карточки на живом примере со спуском до конкретного метода. Затем: что такое сервис, типы сервисов, три подхода к мониторингу БД, метрики и агрегации сервиса.

**Ключевое:**
- Открытие проблемы: 3 превышения базовой линии за 5-минутное скользящее окно; закрытие: возврат в норму за 5 замеров; авто- vs ручное закрытие (демо: 97 проблем за 72 ч).
- Типы проблем по критичности с иконками: недоступность, ошибки, замедление (черепашка), нехватка ресурсов (градусник), кастомные.
- Каналы оповещений: почта, JIRA, Telegram/мессенджеры, веб-хуки.
- Карточка проблемы (демо): заголовок с типом и временем, уровни затронутых сущностей; блок «Анализ влияния на бизнес» (расчёт пострадавших пользователей через сессии); «Путь визуального разрешения» (проигрывание распространения проблемы во времени как видео).
- Спуск по root cause (демо): БД → распределение времени ответа; Authentication Service → анализ времени отклика (~10 с, почти всё на сетевом I/O) → hotspots методов → stack trace → `socket read` ждал сети.
- Что такое сервис: логическая сущность на уровне HTTP/SQL/RPC-запросов; без запросов исчезает.
- Типы сервисов: веб-сервисы (Spring Boot, Tomcat), сервисы веб-запросов (Nginx, Apache, IIS), пользовательские, фоновые, RPC/gRPC, БД, очереди (Kafka, Rabbit).
- Три подхода к мониторингу БД: N+1 (без агента в процессе БД, транзакции со стороны бэка через JDBC/ODBC), расширения (внутренние метрики СУБД), инфраструктурный агент (сеть/RAM/CPU).
- Метрики сервиса и агрегации: время отклика, fail rate, throughput, CPU на запрос; медиана vs среднее; перцентили 90%/95% как «самые медленные 10%/5%».

**Практика:** домашнее задание, посмотреть свои сервисы и сколько запросов обрабатывают; ручное закрытие проблемы требует резолюции; хранилище сырых данных на ФС расширяется до 10 дней (дальше только агрегаты); для тренда по 90/95 брать интервал от 24 ч; на хост БД ставить агент в режиме инфраструктуры.

**Оговорки:** имя продукта («астрон/остром») и термины врут: «трафировка» = трассировка, «ход-споты» = hotspots, «Ease» = IIS; вывод про сетевую причину в authentication это гипотеза ведущего; ведущий отметил опечатку в интерфейсе (подписано «среднее», считается медиана). Файл кончается на перерыве, тема продолжается в части 2.

## День 2, часть 2 — Инструменты анализа сервиса, обнаружение аномалий, SLO

**Суть.** Все инструменты анализа отдельного сервиса (от метрик на графике через хотспоты, трассировки, бэктрейс и поток обслуживания до раздела «Анализ»), затем настройки сервиса (правила именования, обнаружение сбоев, тонкая настройка обнаружения аномалий) и механизм SLO с бюджетом ошибок.

**Ключевое:**
- Метрики сервиса и своя палитра инструментов под каждую; анализ времени отклика (хотспоты, куда девается время, паузы на GC, медленный код, разворот до метода; гистограмма распределения, 10% самых медленных).
- Анализ частоты отказов: разбор 500-х (демо: Calculate Recommendations).
- Трассировки: дерево вызовов сверху вниз (фоновый сервис → Apache → Tomcat → БД), таймлайн (жёлтое = запрос в базу, синее = работа сервиса), красным шаги с ошибкой; детали (хост, IP, URL, заголовки, уровень кода) + вкладка «Логи» с автопривязкой log4j.
- Бэктрейс (обратная трассировка): кто вызывает сервис. Поток обслуживания (service flow): топология вызовов в разрезе времени отклика/пропускной способности.
- Раздел «Анализ»: поиск запросов по всему окружению, метрика/агрегация/измерения/фильтры, «Сохранить вид», преобразование в расчётную сервисную метрику (демо упёрся в лимит 100 сервисов).
- Ключевые запросы: детальное и долгое хранение, свои пороги, готовые плитки; при пометке история сбрасывается.
- Настройки сервиса: правила именования (маскирование uid/IP, схлопывание запросов по маске), обнаружение сбоев (учёт 400/500), исключения.
- Обнаружение аномалий на сервисе: авто/фиксированный порог, связка абсолютного + относительного порога, отдельная планка для 10% медленных, шумоподавление, падение/скачок нагрузки (по умолчанию выключены), базисный период 7 дней.
- SLO: доступность в процентах, формула (успешные / общие) × 100, фильтр по entityId или тегу, целевое значение + бюджет ошибок (демо: SLO 100%, бюджет 0,49%).

**Практика:** переименовывать сервисы только через правила, не вручную; в SLO фильтровать по entityId (не по имени) или по тегу для группы; глобальные настройки аномалий трогать осторожно (из коробки рабочие), локально безопаснее; детекцию падения нагрузки включить вручную; после пусконаладки сбросить базисный период; заглушать хелс-чеки и пинги; преобразовывать анализ в метрику, если нужны дашборды/пороги/долгое хранение.

**Оговорки:** демо расчётной метрики не завершилось (лимит 100 сервисов); «избежание сверхпосещаемости» = неудачный перевод, по смыслу шумоподавление; «PowerLAM» вероятно PurePath; ведущий не уверен в ряде величин (шаг «5 минут по-моему», «log4j по-моему»).

## День 3, часть 1 — Мониторинг реальных пользователей (RUM): веб и мобильные, сессии, USQL

**Суть.** Раздел «Приложения / Фронтенд»: как заводятся веб-приложения (через JS-агента), как читать метрики производительности и поведения пользователей, как проваливаться в сессию и в один клик уходить в бэкенд-трассировку. Язык запросов USQL для своих метрик и воронок, коротко мониторинг мобильных (крэши). Всё на демо TravelUp.

**Ключевое:**
- Два способа завести приложение: через дефолтный `MyWebApplication` (выделить домен) или через «Обнаружение приложений» (правила по URL/домену с приоритетом; демо: `кинопоиск.yandex.ru` выше `yandex.ru`).
- Best practice: дробить сайт на логические приложения (каталог, ЛК, справка).
- Инфографика: производительность (по браузерам, роботам Google/Bing, влияние на SEO; карта по геолокации в разрезе Apdex) + поведение пользователя (новые/вернувшиеся, пиковые часы, показатель отказов, конверсии/цель Checkout).
- Ошибки как главный фактор Apdex: запросов (500/401/403/404), JS, кастомные.
- Топология потока обслуживания (демо): браузер → прокси → Apache → Tomcat (бронирование/поиск/валидация карты) → БД.
- Сессии: фильтры, live, водопадный анализ действия, переход в один клик из фронта в бэкенд-трассировку с SQL.
- USQL (демо: метрика `USCM.count_norway`, воронка); мобильные: крэши со stack trace (демо: Samsung Galaxy S6 Edge).

**Функции:** `MyWebApplication` не трогать (частая ошибка клиентов); Load/XHR/Custom Actions; Apdex ≈ (действия без ошибок / все), приемлемо от 0,85 (сверить: официальная шкала 5-уровневая); конец сессии по бездействию ~30-35 мин / 200 действий; ключевое действие пользователя (лимиты 100 на приложение, 500 на окружение); USQL без join, таблицы UserSession/Action/Event/Error, свои метрики с префиксом `USCM.`.

**Практика:** лайфхак USQL, наложить фильтры на экране сессий → «Запрос сессий пользователей» даёт готовый запрос; в воронке действия строго по порядку; счётчику сессий на месяц доверять осторожно (экстраполяция).

**Оговорки:** Абдекс = Apdex, Сидиены = CDN, DOAM = DOM; ведущий не уверен в таймауте сессии (30 или 35); формула Apdex и порог по памяти.

## День 3, часть 2 — Финал курса: настройки RUM, дашборды, автотеги, кастомные оповещения, синтетика, AppSec, атрибуты запросов

**Суть.** Настройки мониторинга веб-приложений (захват сессий, конфиденциальность, теги, инжект агента), работа с дашбордами и плитками. Подробно, сквозной сценарий кастомного оповещения по любой метрике (событие → фильтр → интеграция) и автоматическое тегирование. Коротко: синтетика, безопасность приложений, атрибуты запросов.

**Ключевое:**
- Воспроизведение сеанса = запись взаимодействия с DOM (не видео), поля ввода маскируются, конфиденциальность (маскирование IP/GPS, opt-in); «контроль затрат» = сэмплирование доли сессий.
- Захват: тег пользователя вместо «аноним» (CSS-селектор/JS-переменная/кука…), именование действий по шаблону, свойства сессии; SPA/Angular требует настройки от разработчиков; rage clicks, цели конверсии.
- Дашборды: фильтры, экспорт-импорт через JSON между кластерами, SLO-плитка (демо: SLO 99.9% при цели 99), ссылка анонимного доступа (кейс: дашборды на ТВ в коордцентре без экрана авторизации), динамические фильтры.
- Плитки: визуализация, контекст (Markdown, изображение), стандартные графики здоровья, USQL, SLO, синтетика, счётчик проблем, таблица логов.
- Автотеги: правила на тип сущности (демо: тег NorwayTeam для хостов с IP на «192.», распространить на процессы); правило-тег крестиком не снять.
- **Кастомное оповещение в 3 шага:** (1) событие метрики (Обнаружение аномалий → События метрик; типы порога: статический / автоадаптивный / сезонная базовая линия; расширенные свойства модели = окно и число выборок; демо: Norway Alert), (2) профиль оповещений (фильтр), (3) интеграция (email / webhook / Telegram / Jira, тело с переменными). Повторять на каждый новый алерт нужно только шаг 1.
- Синтетика (браузерный и HTTP-монитор, запуск с ActiveGate); модуль App Security (уязвимости кода и библиотек, обновление баз в air-gapped через зеркало); атрибуты запросов (демо: Journey ID / Client IP).

**Практика:** для своих событий тип «custom»; расширенные свойства модели (окно/выборки) только у кастомных событий (у системных всегда 5 мин/3 замера); дашборд переносим через JSON; логи выводить как метрику, не таблицей; синтетика и security работают в закрытом контуре через шлюз/зеркало.

**Оговорки:** демо-оповещение Norway Alert так и не сработало (мало данных для базовой линии); USKL/USPM = USQL; Abdex = Apdex. Это последняя часть 3-дневного курса.

## День 4 — Прикладное занятие на данных клиента (страховая): сессии, веб-визор, сквозные трассировки, разбор проблемы

**Суть.** Первый час, повтор архитектуры (ноды, хранилища, шлюзы, единый агент) и работа JS-агента RUM. Дальше, по запросу бизнеса, практика на живых данных клиента (страховая, ЛК РГС): пользовательские сессии и веб-визор для реконструкции дефектов, сквозные трассировки фронт→бэк, блок «Проблемы» с ИИ-базовыми линиями и анализом влияния на бизнес. Часть плана (метрики, источники метрик, дашборды) сдвинули на день 5.

**Ключевое (новое относительно дней 1-3):**
- JS-агент RUM вживую (демо DevTools Network): стаб `Ruxit Agent.js` → подгрузка полного агента ~80 КБ по запросу; sync/async (`deferred`); запросы шлются только на действия пользователя, не периодически (в отличие от Яндекс.Метрики).
- Веб-визор: запись взаимодействий с DOM (не скринкаст), реконструкция страницы из статики; поля ввода и аргументы SQL маскируются по умолчанию (разблокировка через согласование с ИБ).
- Инъекция на бэке: автодетект Nginx/IIS/Java/.NET/PHP/Go, Python (авто с версии агента 313), Node.js (в рантайме после деплоя); Java через JVMTI, код-уровень через LD_PRELOAD.
- Поиск и разбор реальной сессии (демо: сессия агента с ОСАГО, ~254 ошибки, действие висело 254 сек): шкала времени, водопад по действию, трассировка фронт→бэк (Nginx → Netty → Node.js → Postgres, виден Istio Envoy).
- Конец сессии: 35 мин после последнего действия / 200 действий / закрытие браузера; связка сессий одного юзера через куки.
- Блок «Проблемы» (демо: инцидент ЛК РГС): ИИ-модель на метриках, базовые линии (часовая/дневная/недельная/сезонная), 5-мин окно выхода за линию → алерт; разбор по блокам (влияние на бизнес → переход в сессии, затронутые сущности, путь визуального разрешения, основная причина, External Systems без агента, прямая и обратная трассировка, связка логов).
- Корреляция со Splunk: если протащить correlation ID в атрибут сессии, логи Splunk можно подтянуть в Ключ (по API или агентом) и коррелировать с трассировками в одном окне.

**Практика / реальные компромиссы клиента:** воспроизведение сессий ограничено лицензией (раздаётся рандомно); с gateway сняли агентов ради экономии лицензий, поэтому он «чёрный ящик» (на пилоте видели всё); имя пользователя сейчас доступно только при авторизации в ЛК, остальные анонимы (нужна донастройка от разработчиков); автосвязку трассировка↔лог клиент отключил, так как вставка trace ID ломала их логи в Splunk; учитывать часовой пояс клиента при поиске инцидента (пример: Благовещенск). Бизнес-кейс группы: по заявке агента объективно восстановить его действия перед дефектом, воспроизвести и отдать разработчикам, плюс проактивно ловить рост ошибок до массовых заявок.

**Оговорки:** «вишкли агрегатор» = vehicle-агрегатор (проверка данных ТС при котировке полиса); «спланк» = Splunk; «ГВ/гайдвара» = gateway; про Apdex тренер и клиент разошлись (тренер «по количеству ошибок», клиент «по срокам ожидания», противоречие не разрешено, официально Apdex по порогам времени отклика); заявление про переработку сезонных базовых линий «в скором обновлении», это про будущее, не подтверждено; последние ~15 мин транскрипта зациклены whisper (про TS-Node), нового не добавляют.

## День 5 — Прикладной разбор на живом стенде РГС: производительность, Apdex, ошибки, дашборды с нуля, теги и зоны управления, поведение пользователей

**Суть.** Финальное занятие, почти целиком на боевой инсталляции клиента (РГС, ЛК РГС, флагман для агентов, ОСАГО) по шарингу экрана, продолжение дня 4. Мониторинг веб-приложения вглубь: анализ производительности и поведения пользователей, Apdex и что на него влияет, разбор реальных ошибок, построение дашбордов с нуля, тегирование и зоны управления, ключевые действия и цели конверсии. Интерактивно: клиент сам тыкает интерфейс, ведущий подсказывает, по ходу находят реальные аномалии.

**Ключевое:**
- Две части мониторинга веб-приложения: анализ производительности и анализ поведения; разбивки по браузерам, типу пользователей (реальные/роботы/синтетика), геолокации (карта мира по Apdex).
- Глубокий разбор Apdex: сравнение периодов (2 ч / 7 / 30 дней / 2 мес), влияние ошибок; вывод, брать короткий период вне зоны проблем с лицензией/агентами.
- Топ ошибок: 404, клиентские/валидационные, HTTP vs JavaScript; исключение «мусорных» ошибок из Apdex; drill-in → stacktrace, source map, список сессий, воспроизведение.
- Метрики здоровья (vitals): полная загрузка, время до интерактивности, LCP; на них строится модель аномалий; усреднение на больших периодах прячет мелкие изменения.
- Backend-причина деградации: «анализ снижения времени отклика», категории (внешний сервис / БД / внутренние методы), method hotspots, водопад; рекомендация еженедельного разбора топ-аномалий.
- Дашборды: базовый health-дашборд из плиток («ячейки реактора»); построение кастомного CPU/память/диск с нуля (фильтр по хосту, пороги-светофор, авто-добавление нод по тегу, «разделить по хостам»); шаринг и разграничение доступа.
- Тегирование (автотеги по IP/имени/ОС, к хостам→процессам→сервисам) + зоны управления (демо: фильтр всего интерфейса по зоне OFR, 5→2 хоста, 109→46 сервисов).
- Действия пользователя (загрузки/XHR/кастомные), ключевые действия (кейс «расчёт тарифа ОСАГО» дробится из-за ID в URL → нужны правила именования); цели конверсии + USQL + воронки + сохранение запроса как метрики с оповещением.

**Практика (реальные кейсы РГС):** Apdex у клиента 0.83-0.84, реально ~0.9 после вычистки клиентских ошибок; пороги CPU-светофора 0/40/80; расчёт тарифа ОСАГО норма &lt;10-12 сек, 95-й перцентиль ~10 с (ночью выбросы &gt;20 с на регламентных задачах); БД мониторится без агента на хосте (нет инфра-метрик БД, пока не поставить агент в режиме инфраструктуры); аномалия геолокации (входы из США/Чехии/Латвии быстрее, чем из РФ → вероятно VPN); Яндекс.Метрику можно убрать (дублирует сбор). Договорились о воркшопе 4-5 февраля (сначала правила именования действий, потом настройка ключевых действий и порогов).

**Оговорки:** абдекс/аптекс = Apdex; «in jinx» = nginx, «кикок» = Keycloak, «БФФ» = BFF, «под споты метода» = method hotspots; USQL прямо не назван, описан как «свой SQL-подобный язык запросов сессий»; числа на слух (971 ошибка, 66%, 109→46) могут быть неточны. Роли: Никита Сабуров (инженер, ведёт демо), Александр (со-ведущий), Андрей и Антон (РГС, тыкают интерфейс), Дмитрий Нетребин (координатор).
