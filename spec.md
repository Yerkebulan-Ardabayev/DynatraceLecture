## 3. ЧАСТИ СИСТЕМЫ

v2 = три слоя поверх v1. Код v1 (crawler, генератор, гейты) не переписываем, только расширяем.

- **A. Freshness Pipeline** (качество материала со временем): crawler v1 как есть + новый `scripts/drift_report.py`, сравнивающий свежее снятие с эталонным `ui_elements.json`. Выход: отчёт «что изменилось, какие темы затронуты» и очередь на переверификацию.
- **B. Lecturer Layer** (качество изложения): `cards/<day>/<topic>.md`, карточка лектора на каждую из 44 тем (схема в разделе 5). Генерация ИИ из explanations, ручная приёмка тона на пилотных, новые CARD-детекторы в `quality_check.py`.
- **C. Presenter Edition** (удобство на звонке): `plan_html.py` собирает ВТОРОЙ одиночный файл `output/training_v2.html` с двумя режимами окна: окно аудитории (его шарим в Zoom/Meet) и окно докладчика (карточка темы, план дня, следующая тема, таймер, запасные планы). Плюс палитра Ctrl+K, полнотекстовый поиск с подсветкой, масштаб шрифта. Текущий `output/training.html` и его сборка НЕ меняются: два варианта существуют параллельно.
- **D. Q&A лектора** (опция, отдельное решение пользователя): локальный grounded-поиск с LLM (BYOK). По умолчанию не делаем.

## 4. ВХОД → ВЫХОД каждой части

**A. drift_report.py**
- Вход: `.env` + `state/storage_state.json` (доступ к демо-тенанту), `config.yaml`, эталон `ui_elements.json`, `study_plan.yaml`.
- Действия: повторное снятие роутов из плана; дифф `main_title`/`headings`; HTTP-статусы роутов.
- Выход: `drift_report.md`: (1) изменённые экраны с диффом заголовков; (2) роуты 404/403; (3) новые заголовки; (4) затронутые темы через маппинг study_plan.yaml. Транзиентные числа-счётчики (Services, Problems и т. п.) помечаются отдельно и дрейфом не считаются.
- Дальше: очередь тем на переверификацию (ИИ: dtkb + /managed/, журнал `tech_claims_verification.md`).

**B. Карточки**
- Вход: `explanations/<day>/<topic>.md` (единственный источник цифр), `study_plan.yaml` (порядок, роуты), `empty_screens_todo.md` (запасные планы).
- Выход: `cards/<day>/<topic>.md` по схеме раздела 5.
- Контракт: любая цифра в карточке обязана присутствовать в explanation той же темы (гейт CARD_UNSOURCED_NUMBER). Карточка не вводит новых фактов, только сжимает проверенные.

**C. plan_html.py v2**
- Вход: всё выше + текущий шаблон.
- Выход: `output/training_v2.html`, один файл, ноль внешних запросов при открытии. Выход v1 (`output/training.html`) остаётся собираемым без изменений (флаг/режим сборки, по умолчанию v1-поведение не трогается).
- Контракт синхронизации окон: окно докладчика открывается через `window.open` из основного, канал `postMessage` по прямой ссылке окна (надёжно на file://); BroadcastChannel и storage-событие как запасные. Сообщение: `{idx}` текущей темы.

**D. Q&A** (если решим): вход: вопрос лектора; поиск: полнотекст по корпусу + dtkb (MCP); ответ строго с цитатой источника /managed/, иначе честное «в корпусе нет».

## 5. ДАННЫЕ

Карточка лектора, `cards/<day>/<topic>.md`, YAML-шапка + 6 блоков:

```markdown
---
topic_id: components
day_id: day-1
timing_min: 12          # предложит ИИ, правит человек
verified: 2026-07-XX
---
## ГДЕ           # маршрут на живом тенанте, 1-2 строки
## ЗАЧЕМ         # зачем тема слушателю, 1-2 фразы
## ЦИФРЫ         # 3-6 ключевых чисел, формулировки из explanation
## ЕСЛИ→ТО       # 2-4 хода «настроишь так → получишь то»
## ЗАПАСНОЙ ПЛАН # что говорить и показывать, если экран пустой/403/изменился
## ВОПРОСЫ АУДИТОРИИ # 2-3 вопроса для вовлечения + короткие ответы
```

- Поиск: по уже существующему `DATA` (имя + html темы), нового индекса не требуется; добавляются ранжирование, подсветка совпадений и прыжок к месту. Никаких CDN и новых npm-зависимостей: палитра и подсветка на ванильном JS.
- Прирост веса файла: карточки 44 × ~1.5 КБ ≈ 70 КБ к текущим ~1.2 МБ. В пределах бюджета 2 МБ.
- Хранилище: git-репозиторий. Новых БД нет. Секреты (`.env`, `state/`) вне git, как в v1.
- Prompt-пресеты: `prompts/preset_<mode>.md` (lecture, instructor, student, customer), каждый наследует запреты CONTENT_POLICY.md.

## 6. СЦЕНАРИИ

1. **Онлайн-звонок (главный).** Лектор открывает training.html, жмёт P: открывается окно докладчика, основное окно шарится аудитории. Стрелки листают оба окна синхронно. Студент спрашивает про retention: Ctrl+K → «retention» → прыжок в тему, совпадения подсвечены; Esc возвращает к текущей теме плана. В окне докладчика всё время: карточка темы, таймер, следующая тема.
2. **Битый экран.** Тема synthetic: живой тенант отдаёт 403. Карточка показывает ЗАПАСНОЙ ПЛАН: показать снимок из курса и проговорить настройку по /managed/. Лектор не импровизирует.
3. **Свежесть перед потоком.** Одна команда drift_report → отчёт: 3 экрана сменили заголовки, 1 роут 404. ИИ перепроверяет затронутые темы по dtkb, обновляет last-verified, гейты зелёные, rebuild. Курс не протухает молча.
4. **Подготовка карточек.** ИИ генерирует 3 пилотные карточки (day-1) → человек утверждает тон → ИИ генерирует остальные партиями по дням, каждая партия проходит quality_check с CARD-детекторами → выборочная ручная приёмка.

## 7. НЕ-ЦЕЛИ v2

- НЕ модифицировать текущий вариант: код сборки v1 и артефакт `output/training.html` остаются рабочими как есть. Вся v2-работа идёт в ветке `v2-presenter` и пишет в отдельный файл `training_v2.html`; откат = игнорировать ветку/файл. Слияние в основную ветку только после пилотного звонка и явного go.
- Stealth-режим и любая «невидимость» для аудитории: не делаем никогда.
- Desktop-приложение (Tauri/Electron), OCR экрана, OmniParser, voice STT/TTS, Qdrant, GraphRAG, Computer-Use-навигация по UI, персонализация по студентам: в v2 не входят (причины в разделе 2). Исследование остаётся референсом для v3.
- Никакого SaaS-контента как доступного в Managed (DQL, Grail, Davis CoPilot, Workflows, Apps). Упоминание CoPilot живёт только в этой спеке как обоснование ниши.
- Не мультиюзер, не веб-хостинг, не мобильная версия: артефакт остаётся одним офлайн HTML-файлом (требование air-gapped показов).
- Не переснимать все 235 скринов «для порядка»: пересъёмка только точечно по показаниям drift_report.

## 11. Риски и контроль

- **Синхронизация окон на file://**: BroadcastChannel и storage-события между file://-окнами ведут себя по-разному в браузерах; поэтому основной канал: `postMessage` по прямой ссылке `window.open`. Приёмка в Chrome и Safari.
- **Публичность репозитория**: карточки и пресеты проходят те же запреты имён клиентов (CONTENT_POLICY, правило 4); перед push широкий grep по каждому known-real-entity имени и производным (урок анонимизации 2026-07-11).
- **Транзиентные счётчики UI**: цифры интерфейса в карточках только с привязкой «на снимке темы»; drift_report по ним не алертит (урок deep QA 2026-06-05).
- **Дрейф UI Dynatrace**: закрывается Ф3; пересъёмка точечная, не тотальная.
- **Вес файла**: бюджет 2 МБ; при превышении сокращать не контент, а служебные данные.
- **Приватность (Ф4 и далее)**: любые записи экрана/звука только opt-in и локально, фильтр секретов до любого облака; `.env`/`storage_state.json` в контекст моделей не попадают.
